## 二、执行顺序纪律

1. **V1/V2/V8 可在编码期随时跑**，属快反馈；
2. **V3–V7 依赖 DSH 运行时**，须在投放后执行；其中 V7 会临时注入缺陷，**执行完必须立即还原并复跑 V6**，防止带缺陷交付；
3. **V9 是最终门禁**，仅在全部前置项通过后执行；
4. 任一验证项失败即视为阶段未完成，禁止以「测试通过非达标」口径降格处理（§二公理 6）。

## 七、附录：施工前定点查证（原阶段五，已并入本阶段）

> 本节收口三项施工前不可推测、必须实测的悬置项。三项结论均已实测闭环：
> S1 —— `tools.guard` 回调为**同步**函数，返回字符串即拒绝（该字符串成为拒绝原因）、返回 `undefined` 即放行，入参含 `name`、`arguments`、`agent`；
> S2 —— 旧目录发现路径已被 DSH 废弃（官方技能原文 `Nothing reads that directory any more.`），现行装载单元为 bundle 声明行；
> S3 —— 技能总数以 `scripts/common/validate-skills.js` 的输出为准，禁止沿用旧文档数字。

### 附录一：S1 `tools.guard` 回调契约

| 项 | 内容 |
| :--- | :--- |
| 为什么要查 | 守卫插件的全部技术可行性建立在 `tools.guard(guard: ToolGuard)` 的入参与返回语义之上；契约不明则无法写出正确实现 |
| 查证手段 | 读工具注册表 Service `tools` 的类型声明与实现；以最小守卫注册观察拦截行为 |
| 通过判据 | 能写出最小 `guard` 注册并观察到拦截行为；若契约不支持路径级校验，**必须回到用户重议方案**，不得改用提示词约束冒充物理约束 |

### 附录二：S2 预设装载单元的发现路径

| 项 | 内容 |
| :--- | :--- |
| 为什么要查 | 决定「单源 → 装载单元」的同步脚本是否必要，以及安装产物能否留在工作区内以规避红线 1 的绝对路径禁令 |
| 查证手段 | 查预设注册服务的发现实现；投放最小预设验证是否被 `list()` 拾取 |
| 通过判据 | 明确回答装载单元形态；不得以「参照实现里出现过」当作契约证据（参照实现只证明写法可用，不证明接口语义） |

### 附录三：`.agents/skills` 的清单真源

| 项 | 内容 |
| :--- | :--- |
| 为什么要查 | 阶段三的登记必须与技能集真源一致，否则文档再次与运行时不符 |
| 查证手段 | 运行 `node scripts/common/validate-skills.js`；比对 `.agents/skills/` 与插件 `skills/` 两处清单 |
| 通过判据 | 得出真实技能总数与物理结构定义，文档按实测数字书写（禁止沿用旧数字而不核实） |

### 附录四：执行顺序与产出纪律

1. S1 优先（阻断编码）→ S2 次之（阻断同步设计）→ S3 最后（只阻断文档）；
2. 每项产出：**查证命令 + 观察到的原始证据 + 结论**，写入验证矩阵的留痕记录；
3. 任一项结论与阶段一/二契约冲突 → 停止施工，带证据回到用户处重议范围；
4. 不在查证结果明朗前创建任何实体文件；不为赶进度跳过 S1。
