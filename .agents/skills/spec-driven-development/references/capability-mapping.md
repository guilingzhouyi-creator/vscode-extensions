# 通用模块能力拓扑分解指南 (Capability Mapping)

## 一、 为什么需要能力拓扑分解
复杂软件需求往往横跨多个职能领域（如领域模型、数据持久化、业务编排、外部交互接口）。若缺乏清晰的分解，容易导致职责交织、循环依赖以及无法独立测试。能力拓扑分解将系统功能分解为解耦的原子模块，并规划单向依赖图。

## 二、 通用分层拓扑架构
通用的模块拓扑自底向上依次划分为：

1. **Shared / Contract 层**：纯数据类型、枚举、通用常量与错误码定义（零外部依赖）；
2. **Persistence / Storage 层**：数据库、文件系统、缓存与远程存储接入；
3. **Core / Engine 层**：业务逻辑、算法状态机、规则评估与聚合计算；
4. **Application / Service 层**：用例编排、生命周期调度与跨模块事务协调；
5. **Interface / Presentation 层**：CLI 命令、API 端点、图形界面或事件监听。

## 三、 拓扑设计三大铁律
1. **依赖单向流动**：上层可以依赖下层，下层严禁反向依赖上层；
2. **核心业务无外部依赖**：Core 核心逻辑必须能在纯内存环境下独立进行脱机单元测试；
3. **接口先行锁定**：在实现上层调度前，先冻结下层的抽象接口定义。
