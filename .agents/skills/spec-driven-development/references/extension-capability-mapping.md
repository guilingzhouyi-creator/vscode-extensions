# VS Code 扩展能力拓扑分解指南 (Capability Mapping)

## 一、 为什么需要能力拓扑分解
大型功能通常由多个子模块共同支撑（如数据模型、存储介质、计算逻辑、界面展示）。直接混在一起开发容易导致职责混乱、互相阻塞和循环依赖。能力拓扑分解（Capability Mapping）将复杂需求拆解为独立的原子能力，并规划一条自底向上的施工路径。

## 二、 VS Code 扩展常见分层拓扑
在开发类似 `workspace-timing` 等 VS Code 扩展时，标准的能力拓扑自底向上依次为：

1. **Shared 契约层** (无外部依赖，纯数据结构与字典定义)；
2. **Storage 协调层** (本地文件 IO、RingBuffer 缓冲与 Journal 日志)；
3. **Engine 计算层** (业务计算引擎、状态迁移机与聚合器)；
4. **Controller 控制层** (生命周期监听、命令调度与上下文联动)；
5. **UI / Webview 表现层** (状态栏渲染、仪表盘消息通信与用户交互)。

## 三、 拓扑规划核心原则
1. **依赖单向流动**：上层模块可以依赖下层模块，下层模块绝不能反向引用上层或全局状态；
2. **纯逻辑可脱机**：Shared、Engine 与 Storage 层必须能在纯 Node.js 环境下脱离 VS Code 宿主运行单元测试；
3. **接口优先**：在实现上层调用前，先锁定下层的 TypeScript 接口定义。
