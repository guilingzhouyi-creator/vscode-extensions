# spec-driven-development — 规范先行驱动开发规范

本技能确立了在编写任何实际生产代码之前，必须先建立结构化技术规格书（Spec）的通用工程工作流。规格书是人类工程师与 Agent 之间的单一事实源（SSOT），它明确定义了我们要构建什么、背后的技术动因、边界不变式以及验收标准。没有规格书的代码编写即是在盲目猜测。

---

## 一、 适用时机与触发条件

在以下任一场景中，必须先执行本技能编制规格书，经批准后方可编码：
1. **启动新功能、新服务或新模块**；
2. **需求存在歧义、边界模糊或不完整**；
3. **变更涉及跨层依赖或多个相互协作的组件**；
4. **进行关键架构设计调整或数据模型升级**；
5. **预期施工复杂度较高、涉及多种状态迁移的任务**。

*免除情形*：纯文本错别字修正、单行安全判空修复、已被完备规格书覆盖的微小局部调整。

---

## 二、 阶段化门禁工作流

规范驱动研发严格划分为四个阶段，必须按顺序推进并在关键决策点获得人类确认：

```text
阶段 0: 范围拓扑分解 ──▶ 阶段 1: 编制规格说明 ──▶ 阶段 2: 原子任务规划 ──▶ 阶段 3: 执行施工 (TDD)
      (Capability Map)          (Feature Spec)         (Task Breakdown)        (Implementation)
             │                        │                      │                       │
             ▼                        ▼                      ▼                       ▼
         确认依赖单向              确认契约完备           确认粒度独立            测试全绿交割
```

### 阶段 0：范围拓扑分解 (Capability Map)
当一项需求包含多个可独立测试的能力模块时，必须先输出模块能力图：
- 每个模块拥有稳定、小写的唯一 `module-id`；
- 依赖关系单向流动，严禁循环依赖；
- 明确自底向上的构建与验证顺序。
详见指南：[capability-mapping.md](references/capability-mapping.md)。

### 阶段 1：编制规格说明书 (Feature Spec)
依据模板 [feature-spec-template.md](templates/feature-spec-template.md) 编写 `SPEC.md`。规格书必须明确包含：
1. **问题定义与业务目标**：解决什么问题，明确非目标（Out of Scope）；
2. **架构角色与分层位置**：在系统中的层级归属，遵循单向依赖；
3. **核心数据模型与接口契约**：明确输入输出数据类型与前置条件；
4. **容灾与边界防御**：极限输入、异常故障、持久化一致性与优雅降级方案；
5. **验收测试矩阵**：覆盖正常流、边界值与故障回退分支。

### 阶段 2：原子任务规划 (Task Breakdown)
将规格书拆解为独立的原子微任务（每个任务聚焦单个文件或紧密耦合对），标明依赖顺序与验收条件。

### 阶段 3：执行施工与多维质量交割 (Implementation & Quality Gates)
在规格书指导下，调用测试驱动开发（TDD）小步快跑编码。
- **资深工程师编写纪律**：控制流平铺直叙（卫语句提前返回）、高频热路径零瞬态堆分配、消融空包跳板、模块首部维护结构化架构契约；
- **多维防线交付标准**：牢记“测试通过仅为必要底线，绝不等同于合格达标”；每项原子任务除确保测试用例全绿外，必须通过静态编译自检与静态分析规则扫描，达成多维防线全部通过后方可交割。
