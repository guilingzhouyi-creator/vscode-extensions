# 跳板文件与多余间接层消融指南

## 一、 跳板文件与多余间接层的识别判据

### 1. 跳板文件 (Trampoline File)

跳板文件本身不承载实质业务逻辑，只做单行转发、透传导入导出或空壳代理（有效代码行通常 $\le 3$ 行）。它徒增代码树深度，让寻址多一跳、认知多一层。命中下列任一条即判定为跳板：

- 文件体只有一个 `export * from` / `export { x } from` / `import` + 原样再导出；
- 文件内没有任何分支、状态、常量或类型定义，只有转发语句；
- 全仓对它的引用都只是把它当作被转发模块的别名，没有人为这一层单独写测试。

### 2. 多余间接层 (Redundant Indirection)

间接层比跳板文件更隐蔽：它有真实的函数体，但函数体只是把参数原样交给下一个函数，不增删语义。

- 纯委托包装：`function save(x) { return store.save(x); }`，无校验、无转换、无日志；
- 单实现接口：接口只有一个实现类，且该实现从不被替换（与「可替换策略」区分：策略注入要求至少两条真实分支）；
- 参数原样传递的适配器：形参与实参一一同名同序，说明它并未做任何适配。

> 判定口径是**是否增加可观测语义**。增加校验、转换、重试、埋点、事务边界都算实质承载，不属于本指南的消融对象；反之，仅仅换了个名字转发不算承载，见 [facade-discipline](../../facade-discipline/SKILL.md) 的 ELOC 与不可变冻结预算。

## 二、 消融三步操作法

1. **全局引用检索**：扫描全仓所有引用该跳板文件（或该间接层函数）的位置，含动态导入、路径别名、配置文件与测试桩；
2. **重定向导入路径**：把每个引用点直接改为被转发的真实目标模块（或调用真实实现），不改动调用方其余逻辑；
3. **物理安全移除**：确认无外部动态导入依赖后删除该文件与其专属测试，再执行全量构建与测试确认零断裂。

三步必须按序完成。先删后改会让中间状态无法构建，一旦中断就留下一棵坏掉的树；先改后删才保证任一时刻仓库可构建。

## 三、 消融后的验收判据

- 构建与全量测试在删除后仍然全绿，且**没有为了让测试通过而修改任何测试断言**；
- 对外导出面要么不变，要么是严格收窄（被删掉的只是转发名）；
- 引用计数归零：全仓再也搜不到被删文件的路径字符串；
- 架构契约注释随实质代码一起搬迁，不随跳板文件一起消失。
