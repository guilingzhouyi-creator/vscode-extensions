# doubt-driven-development — 怀疑驱动开发与对抗性复审规范

本技能确立了在软件工程关键决策中实施对抗性反思与证伪的通用工作流。**自信的回答不代表正确的回答**。长时间的编码和推理往往会在不知不觉中将假设当成既定事实。怀疑驱动开发是一种在开发过程中的对抗性姿态：在非微小的设计与代码交付前，主动假设施工作者存在盲区与自满，通过系统化证伪来挖掘隐藏的缺陷与失效模式。

---

## 一、 适用时机与触发条件

决策在满足以下任一特征时被认定为**非微小决策**，必须激活本技能进行对抗性核验：
1. **引入或重构核心分支与控制流**；
2. **跨越模块边界、子系统边界或外部接口契约**；
3. **断言编译器/类型系统无法静态验证的属性**（如并发线程安全、幂等性、时序不变式、最终一致性）；
4. **正确性依赖于未来读者无法一眼看清的隐含上下文**；
5. **影响半径不可逆或修复代价极高**（数据迁移、底层协议变更、公共 API 发布）。

*免除情形*：纯机械性重命名、无逻辑变更的代码格式化、纯单行显然正确的修复、用户明确要求极速探索时。

## 二、 核心怀疑五步循环 (Doubt Cycle)

```text
1. 声称 (CLAIM) ──▶ 2. 隔离 (EXTRACT) ──▶ 3. 证伪 (DOUBT)
                                                │
                                                ▼
5. 收敛 (STOP)  ◀── 4. 仲裁 (RECONCILE) ◀───────┘
```

### 1. 声称 (CLAIM)
用 2~3 行精炼技术语言明确表达当前做出的核心技术断言及其重要性：
- 断言内容：例如“该缓存调度器在高并发读场景下具备确定性淘汰且无数据竞争”；
- 为何重要：例如“此处的竞态会导致核心数据脏读，在单元测试中极难稳定捕捉”。

### 2. 隔离 (EXTRACT)
向审查者仅提供**产物 (ARTIFACT)** 与**刚性契约 (CONTRACT)**，严禁夹带作者的主观推导心路历程。
- 代码级：只提供变动函数或 Diff 切片，而非全量文件；
- 契约级：只提供必须满足的前置后置条件与边界约束。
若将个人结论一并提交，审查者将不可避免地陷入顺从验证（Validation Bias）而非独立审视。

### 3. 证伪 (DOUBT)
以**对抗性提问（Adversarial Inquiry）**驱动审查：
- 审查目标仅为**找茬与证伪**，严禁进行礼节性称赞或总结陈词；
- 重点排查：未明说的隐含假设、未处理的极端边缘输入、隐藏的全局共享状态、对上层契约的潜在违背、现有调用约定的破坏。

### 4. 仲裁分类 (RECONCILE)
审查者反馈的技术事实是参考数据，必须按优先级客观分类处理：
1. **契约不明确 (Contract Misread)**：审查者因契约表述不清而质疑，优先修正契约定义；
2. **真实且可执行缺陷 (Actionable Defect)**：确实存在未防御漏洞，立即修改产物并重新复核；
3. **合理架构权衡 (Valid Trade-off)**：缺陷客观存在但修复开销远大于收益，显式记录权衡理由；
4. **环境噪音 (Noise)**：基于未暴露的已知事实而产生的误报，确认无害后予以忽略。

### 5. 严格收敛停机条件 (STOP)
怀疑循环必须受控收敛，满足以下任一条件时立刻终止循环：
- 审查反馈仅剩琐碎建议或已知权衡；
- 完成最多 3 轮循环（若 3 轮仍有实质冲突，说明产物粒度过大或设计存在根本分歧，必须上报人类）；
- 人类工程师明确下达放行指令。
