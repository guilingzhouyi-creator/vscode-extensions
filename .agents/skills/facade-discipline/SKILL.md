# facade-discipline — 门面层实质承载与跳板消融工作流

本技能规范了门面（Facade）、网关（Gateway）与统一导出入口的架构设计标准，防范空壳代码膨胀。

---

## 一、 空包跳板拦截与物理消融 (`ARCH-ABS-001`)

### 1. 空包跳板判定特征
- 源码文件（`.ts` / `.js`）仅包含 `export * from './sub'` 或 `export { ... } from './sub'`；
- 除头部注释外，有效代码行（ELOC）$\le 3$ 行；
- 文件内无任何本地声明（无 `function`、`class`、`interface`、`type`、`const`、`let`、`var`、`enum`）；
- 仅向单一目标转发导出。

### 2. 标准消融作业流
- **禁止创建**：重构或重命名文件时，严禁自造此类中间兼容垫片；
- **存量消融**：全库检索并替换所有对该跳板的直接调用点至底层真实源头，随后使用 `git rm` 彻底物理删除该跳板文件；
- **全域守卫**：全工作区运行 `validate-no-empty-scripts.js` 确保跳板数为 0。

---

## 二、 门面层实质承载标准 (`ARCH-FAC-001`)

任何命名包含 `facade`、`gateway`、`adapter` 或作为顶层公共导出入口（barrel）的模块，必须满足以下硬性条件之一：

1. **运行时模式守卫与数据契约校验**：
   - 包含显式类型断言或验证函数（如 `assertValidProfile`、`assertValidPayload`），拦截脏数据向内层渗透；
2. **不可变性封装保障**：
   - 关键返回数据与配置对象必须接入 `Object.freeze` 或 `deepFreeze`，防止调用方发生越权突变；
3. **多领域实质聚合与高代码密度**：
   - 聚合 $\ge 3$ 个正交子领域模块，提供统一业务编排；
   - 有效代码行必须满足 $\text{ELOC} \ge 15$ 行预算；
   - 若仅透传 1~2 个子模块且无任何校验逻辑，必须消除该虚空门面，让调用方直连具体实现。

---

## 三、 认知负担与跳转惩罚模型

在静态质量评估与技术债核算中，跨层调用链每增加一层无实质承载的空包转发，将产生认知跃迁惩罚（$\text{HopPenalty} = +3.0\text{ units/hop}$）。架构设计应保持控制流与数据流直达，坚决消除多层跳板。
