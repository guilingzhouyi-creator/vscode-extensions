# WebGames 后端代码注释统一规范（backend 全库）

> 适用范围：`WebGames/backend/**/*.gd`（domains 47 业务域 + contract_registry/lifecycle 基础设施域 + infrastructure 全部层）。
> 目标：注释完整完善、排版规范化、与具体代码行号对齐、区块集中分割、解释到位。
> 门禁对照：`audit_gd.py` HEADER_MUST（文件路径/职责）+ NAMING 命名规范，本规范为其注释维度的细化执行标准。

---

## 一、文件头块（每个文件 L1~9，必填）

标准四段式（已有文件按此补全对齐）：

```gdscript
# ==============================================================================
# 领域：<领域名>（<英文类名族>）| 基础设施：<层名>
# 文件路径: res://backend/<相对路径>
# 职责: <2~5 行>——说明该文件核心职责、关键契约、配置驱动来源（config/<层>/<名>.json）、
#       以及边界约定（如「仅联机可用」「幂等」「确定性」）。禁止空泛描述。
# ==============================================================================
```

要求：
- `# 文件路径:` 必须与 `res://` 实际路径逐字一致（audit_gd HEADER_MUST 强制）。
- 职责至少覆盖：做什么 / 数据或配置从哪来 / 与相邻模块的边界。
- 头块后空一行再 `class_name` / `extends`。

---

## 二、区块集中分割（文件内分区）

类内部按逻辑分区，使用统一分割线（与头块同宽 78 字符）：

```gdscript
# ==============================================================================
# 一、常量与枚举
# ==============================================================================

# ==============================================================================
# 二、状态与依赖注入
# ==============================================================================

# ==============================================================================
# 三、生命周期（_init / _ready / 销毁）
# ==============================================================================

# ==============================================================================
# 四、核心算法与业务方法
# ==============================================================================
```

要求：
- 分区标题用中文序号（一/二/三…），同一文件内分区编号连续。
- 短文件（<40 行）可不分区，但至少保留「核心方法」区。
- 分区之间空一行，分区标题行上方空一行、下方空一行。

---

## 三、方法/属性文档注释（`##` 双井号，Godot 文档注释）

紧贴所描述符号**上一行**（行号对齐原则：注释行号 = 符号行号 - 1，不允许漂移或隔行）：

```gdscript
## 方法一句话职责（动词开头）。
## 契约（Phase XX / Inv-XX）：边界条件、失败语义、配置键来源（config/xxx.json 的 key）。
## 性能：循环内禁止瞬态分配等红线提示（若有）。
func do_thing(...) -> void:
```

要求：
- 每个 `func` / 关键 `const` / 关键 `var` 至少一行 `##` 文档注释；纯 getter/setter 可一行概述。
- 含算法/状态机/求解器的方法必须写「契约」行：输入前提、输出语义、异常路径。
- 注释与符号之间不得有空行（否则行号不对齐）。

---

## 四、行内解释注释（`#` 单井号）

只解释「不读代码看不出的意图」，不逐行翻译代码：

```gdscript
var x: int = _rate(COIN_GOLD) # 战略能源高阶本位货币（与 config/currency.json 比率联动）
```

要求：
- 行尾注释：代码与 `#` 之间**一个空格**，`#` 后一个空格再写内容。
- 同一逻辑块的行内注释上下对齐（列对齐可选，不做强制，避免过度排版）。
- 禁止：无意义的「# 定义变量 x」式逐行翻译注释。

---

## 五、解释处（复杂逻辑）

- 状态机：每个状态枚举项一行注释说明触发条件；转移处 `# 触发：xxx → yyy`。
- 算法/公式：关键步骤上方 `# 第 N 步：…` 或行尾 `# …原因`。
- 边界守卫：`# 防 xx（负数/空/越界/双写）` 注明防什么。
- 兼容/迁移：`# 旧档兼容：字段缺失按默认补齐（Phase 31 S3）` 注明出处。
- 禁止在解释处使用 `TODO/FIXME/XXX/HACK`（audit_gd PENDING_MARKER 门禁）。

---

## 六、排版硬性规则（对照 audit_gd）

| 项 | 规则 |
|---|---|
| 缩进 | GDScript 制表符（1 tab）；注释随代码缩进对齐 |
| 行宽 | 注释行尽量 ≤ 100 字符（分割线 78 字符固定） |
| 换行 | LF（.gitattributes 已强制 `*.gd eol=lf`） |
| 头块缺失 | 零容忍（audit_gd HEADER_MUST） |
| 未决标记 | 零容忍（`TODO/FIXME/XXX/HACK` 一律收敛为 Phase 编号） |
| 文案 | 中文注释为主，代码标识符保留英文 |
