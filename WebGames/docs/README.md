> [!IMPORTANT]
> **【体系区分与短期施工铁律】**：
>
> 1. **历史卷体系 vs 分层施工体系**：后端 43 卷与前端 17 卷为**已全量验收封存的历史案卷**；当前活跃研发全面采用**分层施工路线图体系**（`01_短期施工区` 与 `02_长期演进区`）。
> 2. **先细则获批，后编码施工（硬性门禁）**：无明确授权时，任何新增施工默认归入 `01_短期施工区/`。**每次改动必须先落成分阶段施工细则（四阶段模板：1.数据契约 ➔ 2.业务实现 ➔ 3.配置驱动 ➔ 4.验收测试），获得项目负责人/用户明确批准后方可编码，未获批准严禁编写代码**。
> 3. **10 案卷周期归档机制**：短期施工区**每完成 10 个施工细节案卷为一个归档周期**（如 05~14 卷、15~24 卷，按实际 Phase 序号命名），经四阶段特化与无样板复制校验后，自动打包归入 `docs/归档库/03_短期施工档案卷/` 编排标准档号（`KALAR-DEV-2026-ST{NN}-{PPP}`），并清理活跃看板。

## 二、硬性规范（门禁自动强制，规则 ID 见 `--rules`）

1. **命名**：文件/目录名必须匹配 `NAMING_RULES` 声明模式；新建目录族必须先在
   `scripts/py/audit_docs.py` 的 `NAMING_RULES` 登记模式再建档（`NAMING-FILE` / `NAMING-DIR`）。
2. **布局**：单一 H1（需求表用 `# <名>（第N卷：<主题>）` 全角括号式）；围栏必须闭合；
   表格各行列数与表头一致、单元格内竖线写 `\|`；表格前留空行；无行尾空白（`LAYOUT-*`）；
   后端需求表必须齐备**四段式标准章节**（一实体 / 二求解器 / 三状态机 / 四验收，`LAYOUT-SECTION-STD`，全库已达标）；
3. **档案头块**：归档库阶段件前 20 行必须含 `档号:` 与 `验收状态` 键值头（`LAYOUT-ARCHIVE-HEAD`）；
   新文档一律套用 `docs/模板/` 三类模板创建（需求表四段式 / 阶段细则 / 分卷索引）。
4. **链接**：一律用**相对路径**，禁止 `file:///`、盘符路径与机器特定绝对路径（`LINK-ABS-FILE-URI`）；
   链接目标必须存在（`LINK-DEAD`）；锚点必须与目标文件真实标题匹配（`LINK-ANCHOR-DEAD`）。
5. **图表**：mermaid 节点标签含 `[ ] { } ( )` 时必须整体加双引号（`MERMAID-SPECIAL-CHARS`）。
6. **行尾**：沿用各文件既有 EOL（sh 一律 LF、ps1 一律 CRLF 为仓库约定）。
7. **两轮施工周期与序号门禁**：
   - **每轮开工前置检查**：每次收到提示词，第一步必须先检查短期施工区，核对序号、状态、上轮完成位置与未完成事项，严格验证序号连续、唯一、无跳号、无重复、无越序；
   - **两轮构成一个施工周期**：第 1 轮（检查 ➔ 编写细节与规划，严禁未经批准编写业务代码，禁止提前改路线图）；第 2 轮（细则获批后复查 ➔ 细则收敛 ➔ 代码实施与全量验收 ➔ 更新路线图总索引闭环）；
   - **强制序号继承**：新任务只能取当前序列中的下一个合法序号，路线图、施工区、代码状态三者必须严格自洽，显式状态为唯一权威依据；
   - **案卷文件结构铁律**：每个案卷目录下严格仅允许包含且必须包含 4 份分阶段施工细则文件（阶段1~4），严禁在案卷目录下自造 `README.md` 或多余文档；
   - **路线图登记唯一真源**：全域仅在 `docs/路线图/路线图总索引.md` 中登记与更新案卷状态；`docs/路线图/01_短期施工区/README.md` 仅作为施工区制度说明规范，严禁向其写入在途任务或案卷列表。
50: 8. **测试工程化规范与拓扑隔离**：
51:    - **`tests/unit/` 零散落红线**：`tests/unit/` 根目录严禁存放任何测试脚本，必须按层归位至 `tests/unit/domains/`、`tests/unit/frontend/`、`tests/unit/infrastructure/`；
52:    - **统一基类与入口契约**：所有测试套件必须继承 `TestCase`（`tests/support/test_case.gd`），统一通过 `static func run_all_tests() -> Dictionary` 与 `TestCase.pack_results` 交付指标；
53:    - **领域契约 1:1 双向对齐**：后端领域测试必须在 `config/infrastructure/domains.json` 登记 `"test"` 路径与启用状态；
54:    - **测试确定性与无副作用**：严禁裸随机 `randf()`/`randi()`，高频循环遵循 `ADV-PRF-002` 零堆分配，测试生命周期前后严格清理。详细规范见 [tests/README.md](../tests/README.md) 与 [docs/模板/GD老练风格硬性规范标准.md](模板/GD老练风格硬性规范标准.md) 第八章。
9. **前端可视化边界（硬性红线）**：
   - **视图零业务计算**：`frontend/views/**` 严禁随机数、汇率/概率/成功率/聚合公式、规则状态机与伪持久状态；
   - **唯一数据入口**：业务数据一律经 `apply_snapshot(snapshot)` 注入，视图严禁自读业务 mock 或 `GameConfig` 业务数值；
   - **单向依赖**：视图只允许依赖 presentation/ui_infrastructure/components/navigation/i18n/theme，严禁直连后端类、`EventBusCore`、网络与跨视图节点；
   - **契约与复用**：快照 DTO 强类型且序列化对等，节点引用用 `@export`/`%UniqueName`，浮层与原子组件优先复用全局管理器。详细规范见 [GD老练风格硬性规范标准.md](模板/GD老练风格硬性规范标准.md) 第九章。

76: **禁止行为（违反即门禁阻断）**：
77: 
78: - 禁止跳号、重号、越序添加任务序号，禁止在细则获批前擅自提前修改路线图状态；
79: - 禁止引入 `file:///` 或任何机器特定绝对路径；
80: - 禁止重命名/移动/删除文档而不同步全库入链 → 通过标准：检索旧名全库零残留后再交付；
81: - 禁止修改/重新生成基线来"消音"新增违规（`--update-baseline` 仅限真实消化存量后使用）；
82: - 禁止在归档/看板文档中臆造与需求表冲突的字段或公式（需求表是唯一真理源）；
83: - 禁止删除规则、放宽 `NAMING_RULES` 或注释审查逻辑来绕过门禁；
84: - **禁止在 `tests/unit/` 根目录直接散落测试文件**（必须按分层归入 domains/frontend/infrastructure）；
85: - **禁止在测试用例中调用裸随机（randf/randi）或在循环内产生临时堆分配**（必须使用 DeterministicRNG）；
86: - **禁止通读总目录（87KB）等大索引定位文件**：定位一律用 `audit_docs.py --manifest` 单行 grep、
87:   路径 glob（目录与文件名自描述），或先读阶段件头 20 行档案头块摘要层再决定是否全文；
88: - **禁止无差别通读全量模板库**：查阅规范必须依据 [docs/模板/README.md](模板/README.md) 推荐的精确行号切片（`view_file` 指定 `StartLine`/`EndLine`），将 Token 消耗从 5,000+ 压降至 200 左右，严禁盲目全量加载。
