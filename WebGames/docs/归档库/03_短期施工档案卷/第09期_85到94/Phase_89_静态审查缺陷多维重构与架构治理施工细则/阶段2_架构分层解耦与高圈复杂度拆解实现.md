## 一、 实施细则方案

### 1.1 领域模型分层解耦（`account_slot_binding_solver.gd`）
- **问题根因**：
  文件 L12 `const GameLoopStateStack = preload("res://backend/infrastructure/game_loop_fsm.gd")` 造成领域层反向依赖基础设施层；并在 L48-49 实例化临时对象（`var stack := GameLoopStateStack.new()`），调用后对象即被销毁，未向任何全局服务注册，属纯多余无效调用。
- **重构方案**：
  1. 删除 L12 的 `preload` 语句；
  2. 删除 L48-49 的 `stack.push_state(...)` 本地无用代码块；
  3. 更新文件顶部头注释中职责说明与依赖声明，移除 `GameLoopStateStack` 描述。

### 1.2 `magic_tier_registry.gd` 圈复杂度拆解（CC 33 $\to \le 5$）
- **原函数**：`_validate_invariants() -> bool`
- **拆分设计**：将杂糅的 5 种不变量校验提取为 5 个独立私有校验子函数：
  1. `_validate_dimension_counts() -> bool`：校验四类维度容器基数（阶位 11 / 能力分级 5 / 称号 13 / 形态 4）；
  2. `_validate_ranks_continuity() -> bool`：校验阶位等级 1~11 严格连续无缺漏；
  3. `_validate_tiers_intervals() -> bool`：校验能力分级 5 条目区间在 1~11 内且 lo <= hi；
  4. `_validate_bands_coverage() -> bool`：校验四档区间互斥且无缝覆盖 1~11；
  5. `_validate_profession_ranks() -> bool`：校验称号连续性与魔术师单调性约束。

### 1.3 `magic_rule_registry.gd` 圈复杂度拆解（CC 31 $\to \le 6$）
- **原函数**：`_validate() -> bool`
- **拆分设计**：提取专项校验逻辑：
  1. `_validate_affinity_matrix() -> bool`：校验元素亲和度矩阵与互斥规则；
  2. `_validate_casting_limits() -> bool`：校验施法时限与阈值数值；
  3. `_validate_synergy_rules() -> bool`：校验协同增幅规则。

### 1.4 `contract_parser.gd` 命令路由重构（CC 19 $\to \le 6$）
- **原函数**：`dispatch_ui_command(cmd: String, args: Dictionary) -> Dictionary`
- **重构设计**：
  1. 构建内部 `_command_handlers: Dictionary[StringName, Callable]` 静态路由表；
  2. 将原长 `match cmd` 分支分别封装为小型 Handler 函数；
  3. 调度入口仅做路由查表与兜底判定，复杂度降至 4。

### 1.5 `currency_entities.gd` 事务守卫抽取（CC 17 $\to \le 6$）
- **原函数**：`apply_transaction(tx: Dictionary) -> Dictionary`
- **重构设计**：
  1. 抽取 `_validate_transaction_payload(tx: Dictionary) -> String`：集中校验事务参数合法性并返回错误码；
  2. 抽取 `_execute_balance_mutation(currency_id: String, delta: int) -> bool`：执行纯粹的数值加减与上下界约束；
  3. 主函数前置守卫检查，成功后流转变更，圈复杂度降至 5。
