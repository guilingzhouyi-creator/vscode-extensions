## 一、 数据结构设计与代码契约 (Data Structures & Code Contracts)

### 1. 幂等缓存键命名空间契约（M3 落点）

```gdscript
# 契约：幂等键 = 复合键（owner_namespace + owner_id + resource_id）
# owner 维度：mail 归属账户（MailItemAggregate.recipient_account_id）
# resource 维度：mail.mail_id（保持与既有调用面兼容）
func _claim_cache_key(mail: MailItemAggregate) -> String:
    # 维度升级：account_id + "::" + mail_id；杜绝跨账户错配
    return "%s::%s" % [mail.recipient_account_id, mail.mail_id]
```

不变量 `Inv-IP-1` 检查清单：任何 static 缓存/注册表，凡键中未含「状态所有者」维度即视为违规（本卷先修 mail；审计项纳入阶段3 工程化登记）。

### 2. 业务单据 ID 唯一性契约（M3 生成侧落点）

`voucher_dispatch_pipeline.gd:33` 默认 mail_id 改为走全域唯一 ID 设施（README 已声明：业务 ID 一律 `UniqueIdGenerator.next_id(prefix)`，同毫秒自动追加防碰撞序号）：

```gdscript
# 改造后默认值：UniqueIdGenerator.next_id("CDK")
# 对比：旧 "%d" % Time.get_unix_time_from_system() —— 同秒必碰撞
# 兼容：调用方显式传入 mail_id 的场景保持原样（外部幂等键由调用方保证唯一）
```

不变量 `Inv-IP-2`：同一信箱（recipient）内不允许出现两条同 mail_id 的投递（配合 `mailbox_manager.get_mail_by_id` 现有拒绝语义，碰撞不再发生）。

### 3. CDK 兑换状态机契约（M4 落点）

```
Code 生命周期（资源维度，取代「先核销后投递」的单向提交）：
   AVAILABLE ──领取请求──> CLAIM_PENDING ──投递成功──> USED（终点）
                              │
                              └──投递失败/超时──> RELEASED（可再次领取）或 RETRY_QUEUED

Account 维度（防重领取，沿用既有 code→account 绑定语义，本卷不改变绑定判定）
```

| 状态 | 语义 | 资源可回收 | 允许动作 |
| :--- | :--- | :---: | :--- |
| `AVAILABLE` | 未领取 | — | 发起领取（置 CLAIM_PENDING） |
| `CLAIM_PENDING` | 已占码、投递在途 | ✅ 超时/失败回滚 | `retry_dispatch` / 超时补偿 |
| `USED` | 投递成功、已核销 | ❌ | 只读 |
| `RELEASED` | 投递失败回滚 | ✅ | 重新领取 |

不变量 `Inv-IP-3`：`current_global_redemptions += 1` 与 history append 必须与投递成功**同点提交**（或在失败路径等量回滚），禁止先推进后悬挂。

### 4. 错误码与补偿字段契约

| 新/复用错误码 | 触发 | 语义 |
| :--- | :--- | :--- |
| `DISPATCH_PENDING`（复用） | 投递瞬时失败 | 进入 retry/补偿队列，码状态保持 CLAIM_PENDING |
| `CODE_RELEASED_AFTER_FAILURE`（新增） | 补偿判定投递不可达 | 码回滚 RELEASED、计数回滚，返回可重试 |
| `CLAIM_CACHE_OWNER_MISMATCH`（内部断言，不对外） | 复合键缺维度 | 防御性自检失败即视为缓存污染，清键重算 |
