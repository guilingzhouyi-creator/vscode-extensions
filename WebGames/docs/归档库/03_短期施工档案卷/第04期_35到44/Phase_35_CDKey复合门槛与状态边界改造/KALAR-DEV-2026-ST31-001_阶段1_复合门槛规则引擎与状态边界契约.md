## 一、数据契约与边界

| 契约对象 | 必须字段 | 不变量 |
| :--- | :--- | :--- |
| EligibilityRule | rule_id、metric_key、operator、value | 规则 ID 唯一；operator 属于配置白名单；判定参数合法 |
| RuleCombinator | combinator（AND/OR/NOT）、rules 数组 | 组合关系只允许配置白名单三种；NOT 作用于单规则 |
| RedemptionDecision | allowed、precise_reason、external_hint | 内部精确原因保留；对外提示统一收敛为无效兑换码类 |
| VoucherState | state（ACTIVE/REVOKED/REDEEMED/EXPIRED） | 门槛未满足不改变状态；仅最终成功进入已消耗 |

核心不变量：

1. **三层分离**：规则引擎能力（解释配置）≠ 具体业务规则（配置定义）≠ 示例配置（仅验证框架，标注非默认业务）；示例配置不得升级为默认业务规则或隐式全局约束。
2. **未达标可重试**：门槛未满足时不得扣除、消耗或作废兑换码，不写核销状态（当前次数、全服唯一标记、账户历史均不动），玩家后续满足条件可重新提交并正常兑换。
3. **防枚举提示**：对外统一「无效兑换码」类提示，不区分兑换码不存在、已失效、已被使用、当前门槛未满足或其他内部判定失败；内部保留精确原因供日志、监控、审计与自动化测试使用。
4. **邮件发放边界**：兑换成功后才允许进入已消耗状态；奖励统一经邮箱系统发放，禁止直接修改玩家钱包/背包资产；任何直接写入账户的旧路径均视为需清理或隔离的非规范实现。

## 二、业务实现与状态机

- 兑换判定流程扩展为：输入规范化 → 频控 → 存在性 → 激活/时效 → **复合门槛评估** → 等级/总量/类型 → 原子核销 → 邮件发放。
- 复合门槛评估（规则引擎能力）：逐条解析配置条件并判定 → 按组合关系（AND/OR/NOT）聚合 → 未达标返回可重试判定（不写任何核销状态）；达标才继续后续核销步骤。
- 提示收敛：所有内部失败码映射到统一对外提示，外部提示不含任何判定细节；内部 `precise_reason` 结构化保留真实原因。
- 奖励路径：核销成功后构造邮件附件（货币/物品载荷），经邮件系统投递；隔离或移除现有直接写账户的 `dispatch_rewards_direct` 路径。

## 三、配置驱动与工程化

- `config/domains/cdkey_voucher.json` 新增 `eligibility_rules` 段（规则列表 + 组合关系 + 判定参数），代码不得新增同义硬编码；规则引擎只解释配置，不内嵌业务条件。
- 示例配置（如最低累计游玩时长门槛）仅用于验证框架支持多条件、组合条件与未达标状态保持，必须显式标注「示例配置非默认业务」，不得成为隐式全局约束。
- 失败原因内部可追踪：`precise_reason` 错误码表结构化接入日志与审计；`audit_config.py` 增加规则段结构校验（未知字段/类型/operator 白名单/组合合法性）。
