## 一、配置映射契约

| 配置段 | 新增或收口字段 | 约束 |
| :--- | :--- | :--- |
| `domains.cdkey_voucher` → `eligibility_rules` | `combinator`（AND/OR）、`rules` 数组（rule_id/metric_key/operator/value） | combinator 只允许 AND/OR；规则 ID 唯一；operator 属于白名单（gte/lte/eq/neq/contains）；判定 value 类型合法 |
| `eligibility_rules.example` 标注 | `example_only: true`、`example_description` | 示例配置（如最低累计游玩时长门槛）显式标注非默认业务，不得被引擎作为隐式全局约束 |
| 失败原因表 | `internal_reasons`（precise_reason 错误码清单） | 内部错误码与对外提示收敛映射在配置/代码注释中成对声明 |

示例（仅验证框架能力，非默认业务规则）：

```json
{
  "combinator": "AND",
  "example_only": true,
  "example_description": "最低累计游玩时长门槛——仅用于验证复合门槛框架，非游戏实际业务默认条件",
  "rules": [
    { "rule_id": "min_play_seconds", "metric_key": "accumulated_play_seconds", "operator": "gte", "value": 3600 }
  ]
}
```

## 二、热重载与快照流程

1. `GameConfig` 完成规则段解析与类型校验后，发布带表名/版本号的快照事件（复用 Phase 31 ConfigReloadResult 机制）。
2. 兑换事务开始时锁定单一配置快照；热重载只影响下一事务，禁止半批次混用新旧规则。
3. 规则段任一字段非法时保留上一份有效快照并输出结构化诊断；生产模式不得静默回退到代码默认值。

## 三、异步、持久化和监控

- 规则判定为同步纯函数（无 IO），未达标路径零持久化写入。
- 兑换失败（含门槛未达标）写入结构化日志：记录 `precise_reason`、`rule_id`、`metric_key` 与判定值，载荷不含账号隐私字段。
- 监控指标至少包括 `eligibility_reject_count`、`redemption_success_count`、`external_hint_emitted_count`，指标名采用 `snake_case`。
- `audit_config.py` 增加规则段结构校验：未知字段、字段类型、operator 白名单、组合合法性与示例标注存在性。
