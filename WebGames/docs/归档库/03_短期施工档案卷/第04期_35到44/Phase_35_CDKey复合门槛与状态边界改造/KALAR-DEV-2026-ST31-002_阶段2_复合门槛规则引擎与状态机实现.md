## 一、实现边界与错误隔离

| 领域 | 实现要求 | 禁止行为 |
| :--- | :--- | :--- |
| 规则引擎 | 无状态静态接口：解析配置规则对象、逐条判定、按 AND/OR/NOT 聚合；规则只解释配置，不内嵌业务条件 | 把示例业务条件硬编码进引擎；新增同义默认常量 |
| 兑换求解器 | `resolve_redemption` 在存在性/激活/时效校验后插入复合门槛评估；未达标返回可重试判定且不写任何核销状态 | 门槛未满足时递增当前次数、写全服唯一标记或账户历史 |
| 提示收敛 | 所有内部失败码映射到统一对外提示（无效兑换码类）；内部 `precise_reason` 结构化保留 | 对外提示暴露不存在/失效/已使用/门槛未满足等可枚举细节 |
| 奖励发放 | 核销成功后构造邮件附件（货币/物品载荷）经邮件系统投递；旧直接写账户路径隔离或移除 | 兑换系统直接修改玩家钱包/背包资产形成第二套发放路径 |

## 二、状态机与提交顺序

```text
输入规范化 -> 频控 -> 存在性 -> 激活/时效 -> 复合门槛评估 -> 等级/总量/类型 -> 原子核销 -> 邮件发放
                                         |未达标                     |失败
                                         +-> 可重试判定（不消耗）      +-> 拒绝（不消耗）
```

- 复合门槛评估：逐条规则判定 → 按组合关系聚合 → 未达标 `precise_reason = ELIGIBILITY_NOT_MET`，`allowed = false`，不触碰任何核销状态。
- 原子核销仍为最后成功边界：仅通过全部门槛与上限校验后才递增次数/写唯一标记/追加账户历史。
- 邮件发放：核销成功后把 `reward_payload` 构造为邮件附件载荷，经 `MailDeliveryPipeline` 投递；`dispatch_rewards_direct` 直接写钱包/背包的路径标记为待清理的非规范实现，本阶段以隔离为先。
- 防枚举映射表：`INVALID_CODE/VOUCHER_REVOKED/EXPIRED/LEVEL_TOO_LOW/ELIGIBILITY_NOT_MET/ALREADY_REDEEMED/ALREADY_USED_GLOBALLY/RATE_LIMITED/GLOBAL_LIMIT_REACHED` → 统一对外提示（无效兑换码类）；内部错误码与 `precise_reason` 保留供日志/审计/测试。

## 三、算法与性能约束

- 规则引擎按 `rules` 数组线性评估，单码规则数量有配置上限；组合聚合使用短路求值（AND 失败即止）。
- 未达标路径零写操作：不分配持久化写入、不产生核销副作用，保证可重复提交语义。
- 邮件构造复用既有邮件模板与附件管线，不重复装配钱包/背包逻辑。
