## 一、数据契约与边界

| 契约对象 | 必须字段 | 不变量 |
| :--- | :--- | :--- |
| RedemptionRequest | account_id、voucher_code、input_metrics | 输入规范化（去空格/大写）；判定指标随请求注入 |
| RedemptionRecord | transaction_id、account_id、voucher_code、result、precise_reason | 成功记录唯一且不可变；失败可重试不产生重复记录 |
| VoucherStateTransition | from、to、trigger、transaction_id | 状态变更单向可追踪；仅最终成功进入已消耗 |
| MailDispatchReceipt | mail_id、account_id、attachment_digest | 邮件投递结果可回查；投递失败可恢复重发不重复入账 |

核心不变量：

1. **流程收敛**：兑换请求 → 资格判定 → 状态变更 → 成功记录 → 奖励投递 为唯一生命周期；不允许绕过任一步骤的旁路路径。
2. **一致性**：成功消耗、兑换记录与邮件投递三者原子一致——投递失败不得让兑换码保持已消耗（可恢复重发），记录缺失不得重复发放。
3. **审计留痕**：真实判定原因、状态变化与关键操作内部留痕（日志/审计），不得暴露给客户端（客户端只见收敛提示）。
4. **防重复奖励**：重复提交（重复请求/重复投递）由事务键与投递回执去重，杜绝双倍奖励。

## 二、业务实现与状态机

- 生命周期状态机：`SUBMITTED → ELIGIBILITY_CHECK → REDEEMED → RECORDED → DISPATCHED`，任一步失败进入可重试失败态（不改变兑换码已消耗状态直到投递确认）。
- 一致性策略：投递失败时兑换记录标记 `DISPATCH_PENDING`，恢复后按投递回执重发；成功记录以 `transaction_id` 唯一。
- 审计日志：每次判定记录 `precise_reason`、状态跃迁与关键操作（核销/记录/投递），结构化入审计存储。

## 三、配置驱动与工程化

- 流程阈值（重试上限/超时/回执保留窗口）由 `config/domains/cdkey_voucher.json` 声明，代码零硬编码。
- 审计日志载荷不得包含账号隐私字段；客户端提示仅经收敛映射。
