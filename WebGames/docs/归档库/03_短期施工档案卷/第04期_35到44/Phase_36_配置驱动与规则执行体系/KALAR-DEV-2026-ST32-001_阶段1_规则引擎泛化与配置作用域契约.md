## 一、数据契约与边界

| 契约对象 | 必须字段 | 不变量 |
| :--- | :--- | :--- |
| RuleScope | scope_type（GLOBAL/VOUCHER/RUNTIME） | 三层作用域职责分离；低层不得覆盖高层语义；禁止隐式继承 |
| RuleDefinition | rule_id、metric_key、operator、value、scope | 规则 ID 在作用域内唯一；operator 属于白名单；判定参数合法 |
| RuleCombinator | combinator（AND/OR/NOT）、rules | 组合只允许白名单三种；NOT 作用于单规则 |
| RuntimeMetrics | metric_key → 值 | 单次兑换运行时数据只注入本层，不落配置、不跨次持久化 |

核心不变量：

1. **规则与业务解耦**：规则引擎只解释配置定义的条件，不内嵌任何具体业务条件；业务规则由配置定义，示例配置不得成为隐式全局约束。
2. **作用域职责**：全局规则（所有兑换生效）、兑换码级规则（该码覆盖全局的同 key 规则）、单次运行时数据（仅本次判定注入）——三层职责互不覆盖、不隐式继承。
3. **组合与参数**：配置表达多条件、组合关系与判定参数；默认行为与边界条件显式声明（无规则 = 默认允许，非法配置 = 受控拒绝）。
4. **兼容与校验**：新增配置具备格式校验、非法配置拒绝、默认值定义与向后兼容策略。

## 二、业务实现与状态机

- 规则评估流程：作用域解析（兑换码级覆盖全局同 key）→ 运行时数据注入 → 逐条判定 → 组合聚合 → 返回判定结果。
- 引擎无状态静态接口：输入（配置规则 + 运行时指标）→ 输出（allowed + 失败规则）；不持有玩家数据。
- 非法配置（未知 operator/缺字段/非法组合）受控判定失败并输出结构化原因，不静默回退默认值。

## 三、配置驱动与工程化

- `cdkey_voucher.json` 的 `eligibility_rules` 段作为全局规则示例；兑换码级规则由兑换码聚合字段承载（本阶段定义契约，落地见阶段2/3）。
- 配置校验规则段结构（operator 白名单/组合合法性/字段完整性）由 `audit_config.py` 承担，泛化到多配置表。
