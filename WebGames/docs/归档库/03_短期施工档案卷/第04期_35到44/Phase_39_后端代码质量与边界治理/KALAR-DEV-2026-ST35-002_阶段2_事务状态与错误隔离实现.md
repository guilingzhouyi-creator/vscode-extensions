## 一、实现目标与迁移边界

以最小必要改造修复已确认的状态和职责断裂，保留既有领域 API 与存档格式。所有新逻辑必须落在现有领域服务或协调器边界内，禁止把跨域业务塞入实体、视图或 `GameBootstrap`。

## 二、命令式实施清单

1. **事务阶段收口**：为库存、抽卡奖励、邮件附件、任务奖励、商店交易和分解统计建立“校验 → 暂存 → 主提交 → 旁路提交 → 完成/恢复”的明确顺序。旁路失败不得伪造主事务成功，重试使用原 `transaction_id`。
2. **完整快照回滚**：在装备槽、所有权、锁定计数和保护符会变化的操作前建立深快照；回滚校验版本和事务键，拒绝用过期快照覆盖较新的合法提交。
3. **交易前置拒绝**：商店库存为 `null`、数量不足、价格或数量为负数时，在扣款前返回稳定错误码；禁止通过空库存分支产生货币变化。
4. **强化与分解边界**：强化流程按配置读取保护符消耗并在同一事务中扣除；分解校验锁定状态和 `lock_count`，产物 ID 通过物品注册表或已登记配置解析，禁止源码常量作为事实源。
5. **GM 权限独立判定**：追缴服务从服务端联机模式、角色等级和权限集合共同判定；调用方传入的 `mode` 只作请求意图，空权限集合不能仅凭等级放行；单机路径明确拒绝并留痕。
6. **密封与审计失败隔离**：entitlement 密封必须使用环境密钥或受控密钥提供器，缺失时失败关闭；GM 审计使用带密钥的签名算法并覆盖规范化 `details`，密钥轮换保留 `key_id` 以支持验证。
7. **错误传播与恢复**：跨域调用统一返回 `DomainResult`；禁止 `catch` 后返回成功默认值。可恢复的邮件/统计投递进入待处理状态并由幂等键恢复，不可恢复错误回滚主事务。

## 三、状态与并发约束

- 同一 `transaction_id` 只允许一个提交者；重复提交必须返回第一次结果，不重复扣款或发奖。
- 提交状态只向前推进；回滚只能作用于本次暂存版本，不能覆盖已经提交的新版本。
- 信号和事件在主提交成功后发布，订阅者异常由事件总线隔离，不反向改变已提交实体。
- 静态缓存改为由服务实例持有的有界记录，并在进程重置、配置重载和过期淘汰时清理；不得以全局静态字典作为永久状态仓库。
