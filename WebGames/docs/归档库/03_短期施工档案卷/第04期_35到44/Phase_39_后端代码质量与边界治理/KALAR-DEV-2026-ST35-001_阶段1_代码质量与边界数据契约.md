## 一、立项范围与问题分级

本卷承接后端代码质量审查，不以个人风格偏好作为改造依据。审查发现按下表分级，后续阶段只处理已列入范围的问题：

| 分类 | 纳入的事实问题 | 排除项 |
| :--- | :--- | :--- |
| 规范违规 | 敏感密钥缺失时使用公开回退值；审计摘要未覆盖 `details`；调用方直接决定授权模式 | 仅是命名或排版偏好的差异 |
| 设计缺陷 | 事务提交前写入邮件、任务、商店或分解统计；库存浅快照无法完整回滚；商店库存为空仍允许扣款 | 不改变既有领域职责和公共 API 语义 |
| 潜在风险 | 追缴权限集合为空时仅凭等级放行；`lock_count` 与保护符消耗未形成闭环；幂等缓存无生命周期 | 不在本卷扩展新的 GM 能力 |
| 性能问题 | 幂等记录无限增长；失败补偿重复扫描库存；热点路径产生不必要的深层复制 | 未经基准证明的通用缓存或并行化 |
| 可维护性问题 | 领域自行拼装结果和错误；销毁产物 ID 硬编码；配置重载可能污染旧快照；测试门禁吞掉真实退出码 | 大规模目录重命名或历史档案重写 |
| 可选优化 | 统一 `Result` 结构、结构化遥测、批量统计提交 | 不为“高级”而引入新的框架层 |

## 二、核心数据契约

| 契约对象 | 必须字段 | 边界不变量 |
| :--- | :--- | :--- |
| `OperationContext` | `operation_id`、`transaction_id`、`actor_id`、`source`、服务端解析出的权限快照 | 权限、联机模式和等级从可信会话及服务端上下文解析，不信任请求体同名字段；请求重试复用同一 `operation_id` |
| `TransactionEnvelope` | `before_snapshot`、`staged_changes`、`after_snapshot`、`commit_state`、`failure_code` | 业务变更先暂存，只有主事务成功后才发布邮件、任务、商店、分解统计和领域事件；失败必须可回滚或标记可恢复 |
| `InventorySnapshot` | 物品所有权、库存数量、装备槽、锁定计数、保护符数量、版本 | 快照是深拷贝并带版本；恢复后所有权、装备槽、锁定和消耗品数量与提交前一致 |
| `AuditRecord` | `operation_id`、`actor_id`、`action`、`mode`、`before`、`after`、`details`、`result`、`key_id`、`signature` | 签名覆盖规范化后的完整载荷（含 `details`）；密钥缺失或版本不支持时拒绝签发，不降级为公开常量摘要 |
| `IdempotencyRecord` | 作用域、幂等键、请求指纹、结果摘要、状态、创建时间、过期时间 | 键按账号和操作作用域隔离；状态可恢复；达到容量或过期窗口必须可淘汰，不能由静态字典无限持有 |
| `DomainResult` | `ok`、稳定错误码、对外提示类别、内部原因、可重试标记 | 对外错误不得泄露权限、密封或判定细节；内部原因只进入审计/遥测；同一错误码在各域语义一致 |

## 三、依赖与职责边界

1. `GameBootstrap.assemble()` 仍是唯一装配入口；事务协调器只能依赖领域服务接口，不反向持有视图或配置加载器实现。
2. 库存、邮件、任务、商店、分解和统计领域各自维护实体不变量；跨域协调只负责顺序、事务键和提交结果传播。
3. `GameConfig` 只提供已登记配置的只读快照；调用方不得从配置字典直接修改运行时状态，也不得把运行时状态写回旧快照。
4. `GMArbitrationAuditService` 是 GM 操作留痕的唯一出口；普通领域事件不得伪造 GM 审计记录。
5. 失败路径必须区分拒绝、可重试失败和需要人工处理的部分成功，不以空字典、空字符串或默认成功值吞错。
