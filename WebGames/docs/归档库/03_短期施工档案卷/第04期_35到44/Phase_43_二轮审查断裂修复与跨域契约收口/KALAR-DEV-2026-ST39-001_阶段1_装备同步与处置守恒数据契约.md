## 二、装备同步数据契约（N1）

### 2.1 容量唯一事实源与镜像义务

* `WearableInventoryAggregate.equipped_slots`（键集 `domains.inventory wearable/slots`：HEAD/CHEST/LEGS/FEET/MAIN_HAND/OFF_HAND/BACKPACK）是**容量计算唯一输入**，不变量：`calculate_total_capacity = baseline_capacity + Σ(穿戴护甲类 ∩ capacity_slots 的 volume_slots)`。
* `EquipmentLoadoutAggregate.slots`（键集 `domains.equipment slots`：含 HANDS/NECK/RING_1/RING_2 超集）是**战备预设视图**。两集合交集即容量相关槽位全集；同步义务仅覆盖交集（NECK/RING_* 不参与容量，容忍不同步）。
* 同步义务落点：`EquipmentFSM.equip_from_inventory` / `unequip_to_inventory` 每次成功提交前后，`inventory.equipped_slots` 与 `loadout.slots` 对交集中的槽位**严格一致**（同槽同实例引用）。

### 2.2 container_state 生命周期（既有约定，本卷补全迁移点）

`UNOWNED → INVENTORY（add_item）→ EQUIPPED（equip_item/loadout.equip）→ UNOWNED（remove_item/unequip_item）→ DESTROYED（处置销毁已穿戴物品）`。本卷新增保证：loadout 侧 equip/unequip 与 inventory 侧状态标记**在同一事务内成对发生**，任一侧失败整体回滚（`inventory.snapshot()/restore()` + `loadout.slots` 浅快照），分歧时返回新增错误码 `EQUIP_STATE_DIVERGENCE`。

### 2.3 换装时序契约（UID 去重约束下的合法次序）

`can_add_item` 含 `_contains_uid` 去重（`wearable_inventory.gd:45`），被移动物品必须**先脱离原容器**再检定，故换装合法时序固定为：
`快照 → remove_item(新装备出背包) → unequip_item(目标槽, 旧装备出穿戴) → equip_item(目标槽, 新装备) → can_add_item(旧装备) → add_item(旧装备) → loadout.equip → 提交确认`；任一步失败按快照整体回滚。卸下时序同理：`快照 → unequip_item → can_add_item → add_item → loadout.unequip → 提交`。

## 三、处置产物实例契约（N3）

* 产物实体数 = `MatterDisposalSolver` 返回的 `yield_slag_ash_count` / `yield_mana_dust_count`（每件经 `ItemInstanceFactory.build_instance` 独立获取权威 UID，前缀 `DSP_`）；`historical item_id` 兼容覆写保留（`MATERIAL_SLAG_ASH`/`MATERIAL_MANA_DUST`，`template_id` 恒为注册表 canonical）。
* 统计对齐：`EVENT_ITEM_FORGED` 记账 count 与实际发放实例数恒等。
* 容量守恒：逐件预检（顺序 add/roll），任一件容量不足 → 整体回滚返回 `INVENTORY_CAPACITY_INSUFFICIENT`，输入物品复原，杜绝产物静默灭失。
* 已穿戴物品销毁：`container_state = "DESTROYED"` + `EquipmentLoadoutAggregate.unequip_item_ref(item)` 双侧同步清槽（新聚合辅助方法，返回槽位名或空串）。
* 死键退役：代码移除 `yield_mass/*` 读取；`config/domains/matter_disposal.json` 同步移除该段（`conversion/*`、`yield_ratio/*` 为 solver 真源保留）。

## 四、monster.killed 事件契约（N2）

* 发射点：`CombatPipelineFSM.execute_action_round` 伤害结算后 `defender.current_hp <= 0.0 and defender.is_monster` 时发射。
* `CombatParticipant` 新增状态字段 `is_monster: bool`（配置兜底 `domains.combat participant_defaults/is_monster = false`；纯状态容器字段，无业务判定）。
* 通道 payload 键：`killer_id`（攻击者 participant_id）/ `victim_id` / `drop_declarations[]`（元素 `{canonical_id, display_name, killer_id}`，canonical_id 取自 `domains.monster loot/default_drop_canonical_ids`，逐项经 `GameBootstrap.catalog().get_prototype` 校验，未登记项跳过）。
* 监听器消费契约（既有 `_on_domain_event` 不变）：新增 `find_active_drop(drop_id)` 查询与 `claim_drop(drop_id)` 出队；拾取便捷入口 `attempt_pickup_from_ground(...)` 组合「查找 → `GroundLootPickupSolver.attempt_pickup` → 成功出队」三步，拾取链与监听器状态闭环。
* 掉落配置段：`config/domains/monster.json` 新增 `loot/default_drop_canonical_ids`（初值取注册表在册物品 `KALAR:MATERIAL:ORE:MITHRIL_ORE`、`KALAR:CONSUM:FOOD:HEARTY_STEW`）。
