## 一、P1：QualityTierRegistry 装配期单例化

### 1.1 现状取证（实施前基线）

- `item_instance_factory.gd:12-24`：`build_instance(proto, display_name, uid_prefix, item_id_prefix="")` 在 `proto.quality_tier > 0` 时执行 `QualityTierRegistry.new()` + `reload_configuration()` + `ItemQualityResolver.new(registry)`——即**每发放一件带品质实例即整表重建一次**。
- `quality_tier_registry.gd:9,19`：`QualityTierRegistry` 构造后须 `reload_configuration()` 才能 `is_ready()`（整表 `get_dict` + 遍历校验）。
- 既有装配先例：`GameBootstrap` 已持 `_magic_registry`/`_magic_rules` 单例（`game_bootstrap.gd:12-13,30-38`），`catalog()`/`magic_registry()`/`magic_rules_registry()` 访问器经 `assemble()` 兜底——P1 循此模式无新增架构。

### 1.2 设计

1. `GameBootstrap` 新增静态成员与访问器：
   - `static var _quality_registry: QualityTierRegistry = null`
   - `assemble()` 内装配 `_quality_registry = QualityTierRegistry.new(); _quality_registry.reload_configuration()`（就绪失败同 MAGIC_RULES_REGISTRY_INVALID 模式阻断？**否**——品质缺失不应阻断全装配，与既有 `MagicTierRegistry` 阻断策略区分：品质走「懒装配兜底」，见 1.3；即 assemble() 仅首次访问时装配，不设为装配成功前置条件）。
   - `static func quality_tier_registry() -> QualityTierRegistry:`（首次调用时装配并缓存，幂等）。
2. `ItemInstanceFactory.build_instance` 签名扩展：
   - 新增可选参 `quality_registry: QualityTierRegistry = null`（置于 `item_id_prefix` 之后，**既有 12+ 调用方零改动**）。
   - 内部：`var registry := quality_registry if quality_registry != null else GameBootstrap.quality_tier_registry()`——单例兜底，杜绝 `new()+reload` 重建热路径。
3. `ItemQualityResolver` 构造注入已装配 registry（`ItemQualityResolver.new(registry)`），resolve 语义不变。
4. **兼容性**：既有直接构造场景（测试如 test_inventory/ground_loot 直呼工厂）经 `GameBootstrap.quality_tier_registry()` 兜底——测试宿主已 `GameBootstrap.assemble()`（test_runner 装配），单例可用；单测隔离场景下该兜底首次调用即装配（开销一次，可接受且确定性不变）。

### 1.3 装配边界决策

- 品质单例**懒装配**（首次 `build_instance` 遇 quality_tier>0 时经访问器触发一次），不进入 `assemble()` 阻断链——理由：品质只影响渲染性快照字段，不构成装配完整性前提（区别于魔法注册表之「规则真源」定位）；懒装配同时避免测试宿主装配开销放大。

## 二、P4：超容裁剪统一（FifoBudget.trim_oldest）

### 2.1 现状取证

- 6 处 `while size() > max: erase(keys()[0])`（阶段1 表），keys() 每轮整表重建 → 溢出 k 条时 O(k×N)。

### 2.2 设计

1. 新增基础设施静态助手（置于 `backend/infrastructure/` 新文件 `fifo_budget.gd`，`class_name FifoBudget`）：
   - `static func trim_oldest(container: Dictionary, max_entries: int) -> int`：`max_entries < 0` 视为无界直接返回 0；`over = size() - max_entries`，`over <= 0` 返回 0；否则 `keys()` **排序一次**取前 over 条逐条 erase（Dictionary 保持插入序，keys()[0..over-1] 即最旧），返回擦除数。
2. 6 处调用点接线（clawback/commission_fsm/gacha/mail/quest_reward_dispatch/equipment_enhancement_solver）：
   - 上限键读取保持既有 `GameConfig.get_int(...)` 路径与缺省值（行为等价，仅把 while 循环替换为单次 trim）；语义「最旧先出」不变。
3. 辅助器自身零配置（纯算法），上限仍由各域配置驱动。

## 三、P7：逐击/逐调用拷贝收敛

### 3.1 multi_cast ctx 冻结共享

- 现状：`multi_cast_solver.gd:60-64` 对 `snapshot_ctx` 逐击 `duplicate()`。
- 设计：`execute_play` 内区分目标模式：
  - `target_mode == "SAME"`（或 SEQUENTIAL 但 target_pool 空）：所有击共用 `hit_ctx := snapshot_ctx`（**零拷贝**）——`MagicSettlementSolver.resolve_attack` 只读 ctx（已核验：仅 `ctx.get(...)`），无 per-hit 写入，共享安全；
  - `target_mode == "SEQUENTIAL"` 且有 pool：仅在该模式循环内 `hit_ctx := snapshot_ctx.duplicate()` 后改 `target_id`（保持现状）。
  - snapshot_mode 冻结（`snapshot_locked=true`）不受影响：冻结发生在 snapshot_ctx 构造，共享只读不破冻结。
- 行为等价：SAME 模式下各击 ctx 内容与改造前逐击 duplicate 后**逐位一致**（因只读无变异）。

### 3.2 magic_rule_registry 查询零拷贝

- 现状：`magic_rule_registry.gd:146-176` 每次查询返回 `_multi_cast/_seal/_ascension/_delay/export 全量 duplicate(true)`。
- 设计：改为返回**内部只读引用**（`return _multi_cast` 等），并在 `reload_configuration()` 重建配置时整体替换引用（写时复制语义）；文档标注「返回值为只读，消费方不得就地修改」——已核验全部消费方（multi_cast/ascension/seal/delay solver）仅读取，无不安全就地写；`export_rule_snapshot()`（168-169 行整表 duplicate）保留为**显式快照导出**语义（遥测/存档用，低频），名称不变。

### 3.3 ground_loot cleanup 单遍过滤

- 现状：`ground_loot_event_listener.gd:49-54` cleanup_decayed 整表重建新数组（filter 每次分配）。
- 设计：改 `var alive: Array = active_drops.filter(func(d): return not d.is_decayed)` 单次 filter + 赋值（已是一次分配；若现状为手写循环 + append 则为同样复杂度）——核验后取实际更优者：若 active_drops 需保持实例身份（drop_id 反查），改为**就地尾部压缩**（两指针交换删除法）保持引用稳定。
