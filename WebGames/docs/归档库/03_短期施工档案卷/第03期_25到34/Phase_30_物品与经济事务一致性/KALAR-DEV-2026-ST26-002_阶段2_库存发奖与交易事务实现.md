## 一、数据契约与边界

- 所有数量入口先做 `is_valid_int()`、`> 0`、最大堆叠和总量溢出校验。
- `InventoryTransaction` 保存变更前深拷贝；提交结果必须包含每个物品和每种货币的实际变更。
- 强化保护符必须属于调用者、被消耗一次且与目标强化事务绑定；锁定数量必须参与分解校验。

## 二、业务实现与状态机

1. 购买/抽卡/领取：校验请求与注册表 → 预检容量和库存 → 预留费用与槽位 → 创建实例 → 一次提交。
2. 装备/卸下：验证实例在背包或目标槽位，先从源容器移除成功后再挂载目标，失败恢复源容器。
3. 强化/分解/处置：校验目标存在和锁定状态，统一读取 `combat_metrics.enhance_level`，产物通过注册表解析并检查 `add_item` 结果。
4. 任务奖励数量原值为 0 时不发放；中途失败回滚已提交子项，返回失败明细。

## 三、配置驱动与工程化

- `pull_count`、`buy_count`、奖励数量上限、邮件容量、强化费用、保护符规则和处置产物全部类型化读取。
- `highest_rarity` 初值取配置允许的最低稀有度；低稀有度结果不得被默认值抬高。
- 统一事务组件通过构造注入 inventory、wallet、catalog，不在服务内部隐式创建依赖。
