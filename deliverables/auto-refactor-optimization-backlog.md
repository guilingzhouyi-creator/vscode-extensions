### 0.6 方法修正：单基线消融会产生"幽灵排名"（重要）

第一版消融在 55 秒的扫描序列**开头只测一次基线**，得到的排序是：

```
GOV-PRF-001 +180.7 ms (28.7%)   GOV-DBG-001 +105.8 ms (16.8%)
GOV-FIL-002  +80.9 ms (12.9%)   GOV-PRF-004  +74.0 ms (11.8%)
```

而**同一批规则**改用**交错基线**（每次消融前重新测基线）+ min-of-5 后：

```
GOV-PRF-001   -7.5 ms (-1.1%)   GOV-DBG-001   +4.8 ms (0.7%)
GOV-FIL-002   -9.5 ms (-1.4%)   GOV-PRF-004   +0.5 ms (0.1%)
四项 Deltas 之和 = 5 ms（远小于基线）
```

**结论修正**：**没有任何单条规则主导成本**。第一版排序完全来自长序列中的 JIT/热漂移。第一版自带的
"加总 1062 ms > 基线 629 ms"就是把这一点暴露出来的信号——消融结果的 delta 之和**必须小于基线**，
否则排序不可用。该自检已写入 `hotpath-ablate` 并会直接打印 `INCOHERENT` 警告。

### 0.7 端到端抖动的直接证据，与容差为何必须分指标

重录基准后**立刻**再跑一次比对（同一份代码、同一台机器、间隔数秒）：

```
第一次（--update）：governance-scan 651.2 ms
第二次（--bench） ：governance-scan 708.4 ms   → +8.8%
```

**同一份代码的连续两次测量相差 8.8%，而相对优化前的真实收益是 −7.7%（705.8 → 651.2 ms）。**
即：端到端指标自身的抖动（~9%）与要测量的收益（~8%）同量级，**任何单次端到端比对都无法证明或否定
个位数百分比的改动**。

由此确定容差策略（已写入 `bench-hot-paths.js` 的 `REGRESSION_TOLERANCE`）：

| 指标 | 容差 | 理由 |

| `governance-scan` | **15%** | 实测自身抖动 ≈ ±9%，用 8% 只会在第一次比对就误报 |

**最终基准**（`bench/hot-paths-baseline.json`，已记录为优化后状态）：

## 0.8 深度归因：整条扫描链路的成本构成（本轮深入审查）

前一轮的分组消融只到"规则组 vs 地板"。本轮继续往下钻，用插桩计数 + 隔离计时把整条链路拆开。

### 8.1 全链路成本构成（128 文件 / 40,194 行 / 1.71 MB）

| 环节 | 实测 | 占总扫描 | 备注 |
| :--- | ---: | ---: | :--- |
| **解析 + 归一化** | **162 ms** | **~28%** | 单次 `parse` 内含原生解析与归一化两步（见 §8.3） |
| 19 条**文件级**规则 | ~154 ms | ~26% | 每条各自完整遍历所有行 ⇒ 19 次全文件行遍 |
| 4 条**节点级**规则 | ~126 ms | ~22% | 76k 节点访问 × 4 规则 ≈ 30 万次调用 |
| 掩码 | ~31 ms | ~5% | 已优化（原 57 ms） |
| 遍历 + 节点分发 | **~6 ms** | **~1%** | 见 §8.2 |
| 文件读取 | ~20 ms | ~3% | 1.71 MB |
| 其余（发现/配置/汇总/Issue 构造等） | ~112 ms | ~19% | **尚未归因** |

**插桩计数（每文件）**：`parse` **1.00 次**、`getRulesForLanguage` 1.00 次、`resolveLanguageProfile` 1.00 次、
`maskedLinesOf` 1.00 次、`governance.finalize` 1.00 次、`visit` **589 次**；`analyze` **0 次**
⇒ **单遍遍历多路复用确实生效，没有 N 倍解析**（这条架构前提经实测确认）。

> 精度说明：`GOV-TYP-002` 同时实现 `checkNode` 与 `checkFile`，因此它同时计入"节点级"和"文件级"两组。
> 两组之和 280 ms 与并集实测 276 ms 的 4 ms 差额即来自此处叠加，属测量噪声内的正常偏差。

### 8.2 推翻一个假设：节点分发几乎免费

| 测量 | 实测 |
| :--- | ---: |
| 遍历全部 AST（0 个分析器） | **5.0 ms** |
| 遍历全部 AST（1 个 no-op 观察者，75,374 次节点访问） | **6.1 ms** |

**75,374 次节点访问的分发开销只有 1 ms。** 所以"30 万次节点规则调用"不是瓶颈——4 条节点级规则的 126 ms
几乎全是**规则内部逻辑**，而非调用开销。优化方向应是"让规则少被调用/早退"，不是"降低调用成本"。

### 8.3 解析层：oxc 未达门槛，且真正的大头是归一化

同一语料、同样入口，两条解析路径对比（best of 5，已预热）：

| 路径 | 原生解析 | + 归一化 | 合计 | 归一化占比 |
| :--- | ---: | ---: | ---: | ---: |
| `typescript`（`ts.createSourceFile`） | **68.3 ms** | +93.8 | 162.1 ms | **58%** |
| `oxc`（`oxc.parseSync`） | **96.1 ms** | +51.6 | 147.7 ms | **35%** |

三点结论（均为实测）：

1. **原生 TS 解析比原生 oxc 快 40%**（68.3 vs 96.1 ms）。oxc 的 Rust 解析优势被 **N-API 边界上的 AST
   序列化/反序列化**吃掉——本语料平均 13 KB/文件，属"小文件多批次"，恰好是边界开销最不利的形态。
   *"底层是 Rust 所以更快"在本层不成立。*
2. **总解析成本仅差 3.8% ~ 8.9%**（多次测量在 174.2 vs 167.6 与 162.1 vs 147.7 之间波动），
   **远未达既定的 >20% 门槛 ⇒ 按既定纪律应止损，不做解析器替换**。
3. **归一化才是最大单块**：TS 路径 93.8 ms（占该步 58%），是整条链路里仅次于原生解析的第二大成本。
   任何解析器替换都无法触及它；**降低归一化成本（按需/惰性物化，只构造当前活跃规则真正需要的节点）
   才是解析层的正确杠杆**。

**附带发现（需单独处理）**：端到端 `issue` 数在两条解析路径下**不一致**——`typescript` 3964 条、
`oxc` 3949 条（**少 15 条**）。而 `src/api.ts` 对该选项的描述是 "byte-equivalent"。**两者在本仓库真实
代码上并非等价**，这与"字节级等价"的既定硬约束直接冲突，应作为独立问题登记（要么补齐适配器语义，
要么修正文档表述）。

## 1. P0 — 结构性重复计算（收益最大，风险最低）

### 1.1 `CMP-*` 四条规则的每行分配（目标：governance 的 497 ms）

四条规则各自完整遍历文件，且**在廉价判据之前先做昂贵的字符串变换**（每行 2–5 次分配）：

| 规则 | 当前每行成本 | 可前置的廉价判据 |
| :--- | :--- | :--- |
| `CMP-EXP-001` | 3 次链式 `.replace()`（`?.` → `??` → 三元）后才数运算符 | 无 `?` 且无 `&&`/`||` ⇒ 直接跳过（绝大多数行命中此条） |
| `CMP-LIN-001` | `.replace(/\{[^}]*\}/g)` + `split` + `map` + `filter` | 不含 `;` ⇒ 直接跳过 |
| `CMP-DEN-001` | 先 `replace(/\s+/g,'')` 造整行副本，**再**数运算符 | 先数运算符（廉价），< 8 即跳过；长度窗口用 `code.length` 近似后再精算 |
| `CMP-CAL-001` | 两个正则 `.test` | 无 `=>` 且无 `function` ⇒ 跳过括号行走 |

**做法**：每条规则循环体首部加 1–2 个 `String.includes` / 单次 `match` 作为门；不改变任何判据语义。
**风险**：低（纯前置门，判据不变）。**收益**：估计可去掉治理规则大部分逐行分配；**需用 `npm run benchmark` 实测确认**（本项为估算，未测量）。
**位置**：`src/core/governance/rules/compressionBounds.ts`。

### 1.2 `computeIncrementalMetrics` 同一内容掩码 3 次（已测量：6 次/比较）

`computeEffectiveLoc`、`computeComplexityProxy`、`extractDependencies` 各自调用一次 `maskSourceText`，
于是**同一份内容被完整掩码 3 次**（每侧），一次比较共 **6 次**。

**做法**：在一次 `computeIncrementalMetrics` 内每侧掩码一次，把掩码视图作为参数传给三个指标函数
（保留无参重载以兼容 `api.ts` 现有导出）。
**风险**：低。**收益**：该路径掩码次数 **6 → 2**。
**位置**：`src/core/intelligence/incrementalMetrics.ts`。

## 2. P1 — 掩码层快路径（泛化收益：4 个语言包 + 治理 + 指标）

### 2.1 "无引号无斜杠行"快路径（已测量上限：70.2% 的行）

`maskLine` 对每行都执行 `line.split('')` → 逐字符状态机 → `out.join('')`，**每行 2 次分配**。
但实测 **70.2% 的行不含任何引号或斜杠字符**，这些行不可能开启注释/字符串/正则。

**做法**：在 `maskLine` 首部加一道门 —— 当 `state.inBlockComment === false && state.quote === null`
且该行不含 `'` `"` `` ` `` `/` 时，**直接返回原字符串**（零分配、零逐字符扫描）。
⚠️ 该门**必须同时校验两个状态位为空**：块注释/多行模板中间的行可以不含任何引号斜杠，却必须继续掩码。

**风险**：低（纯快路径；状态位为空时结果与原路径逐字符等价）。**收益**：估计掩码 67 ms → ~25–30 ms
（**估算，需实测**）；同时降低 GC 压力，受益方是所有掩码消费者（4 个语言包 / 治理 / 指标）。
**位置**：`src/core/sourceMask.ts` 的 `maskLine`。

### 2.2 `GovernanceAnalyzer` 的双份行拆分

`ensureInitialized` 里 `ctx.content.split(/\r?\n/)` 取 `lines`，随后 `maskedLinesOf` **又拆一遍**。
而 `maskSourceText` 本来就返回 `raw`。

**做法**：`lines` 直接取掩码结果的 `raw`。两者对 LF/CRLF 结果**等价**（`split(/\r?\n/)` 与
`split('\n')`+剥尾 `\r` 都得到无 `\r` 的行），唯一差异是"文件以孤立 `\r` 结尾"这一极端情形，可忽略。
**风险**：低。**收益**：每文件省一次整文件拆分与一个数组。
**位置**：`src/analyzers/governance.ts`。

### 2.3 无适用规则时不做掩码

语言收窄后，`.py` / `.rs` / `.gd` 文件不再有任何 `CMP-*` 文件级规则，但仍在掩码。

**做法**：`ensureInitialized` 中仅当 `fileRules.length > 0` 时才构建掩码（否则置空数组）。
**风险**：极低。**位置**：`src/analyzers/governance.ts`。

## 3. P2 — 工具链：`npm test` 的 32 次串行进程（已测量启动下限 ≥12.6 s）

`npm test` 是 32 段 `&&` 串联，每段 = 一次 npm 包装 + 一次 node 启动 + 一次 `require(dist/api)`。
实测纯 node+api 启动下限 ≥12.6 s，加上 npm 包装开销，`npm test` 约 150 s 里估计 **13–15% 是纯启动**。

三条可选路径，按风险递增：

| 方案 | 做法 | 风险 | 收益 |
| :--- | :--- | :--- | :--- |
| **C1（低风险，建议先做）** | 加一个 `--only <suite>` 选择器，本地只跑受影响的套件；CI 保持全链 | 低 | 本地迭代时间大幅下降 |
| **C2** | `gate` 已 `build` 过一次，`pretest` 又跑第二次完整 `tsc` ⇒ **去掉重复构建**（用 `dist` 时间戳/校验和后决定是否跳过） | 低 | 省一次完整 `tsc` |
| **C3（中风险）** | 32 个验证脚本改为可被一个进程内 runner 依次调用（各自导出 `run()`，去掉顶层 `process.exit`） | 中：脚本目前是独立 main + exit，需逐个改造 | 省掉 31 次 node/npm 启动（约 12 s+） |

**位置**：`package.json`、`scripts/validate-*.js`。

| `PRF-LEAK-001` 语言扩展 | 集合声明识别当前为 JS/TS 形态 | 补 Python/Rust/GDScript 夹具后再扩声明 |
| oxc-parser 解析层加速 | 用户既定目标（> ts 基线 20% 才采纳） | 走既有等价性闸门 + MIXED 基线 + 中位数采样协议 |

## 6. 建议的执行顺序

1. **§1.1 + §1.2**（去重复计算）——收益最大、语义不变、可用 `npm run benchmark` 直接量化；
2. **§2.1**（掩码快路径）——泛化收益，覆盖全部内容型分析器；
3. **§3-C1 + C2**（工具链低风险两项）——立刻改善日常迭代与门禁耗时；
4. **§2.2 + §2.3**（分析器侧小项）；
5. **§4**（局部细节，顺手做）；
6. **§5**（能力补齐，按产品优先级单独排期）。

**统一验收口径**（沿用本项目既有协议）：每项改动前先跑 `npm run benchmark` 取基线，改动后要求
**等效性闸门通过 + MIXED 基线不劣化**；收益未达门槛则止损，不做"看起来更快"的合并。
