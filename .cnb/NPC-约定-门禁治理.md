## 1. 固定门禁顺序（任何人改动后必须按此顺序验证 · 打勾检查单）

```
☐ [ ] ① npm install → 通过标准：exit 0 且依赖完整
☐ [ ] ② npm run compile → 通过标准：exit 0 且 0 error
☐ [ ] ③ npm run lint → 通过标准：0 error 0 warning
☐ [ ] ④ git diff 自查 → 通过标准：改动与意图一致、无临时文件
☐ [ ] ⑤ 产物一致性 → 通过标准：out/ 与 src/ 同步（无遗漏/过期产物）
```

**规则**：
1. 顺序**不可调换**（铁律 R4）：先可编译，再质量，后审查。
2. 任何一处失败即停，修复后**从头重跑**（不是从失败点继续）。
3. 全部 `[x]` 才可宣称「门禁全绿」；未过标准不得进入合入。

## 2. 构建执行顺序（多人协作场景）

| 阶段 | 动作 | 执行者 |
|------|------|--------|
| 1. 基线构建 | 先产出可编译基线（确认仓库当前可编译） | 协作员·构建 |
| 2. 分领域开发 | 各自主责改动 + 各自门禁自查 | 三个 NPC 并行 |
| 3. 交叉审查 | 按序定点修复，修复后重跑门禁 | 按序三人 |
| 4. 收尾验证 | 最终全量构建 + 门禁全绿确认 | 协作员·审查 主持，构建职能执行 |
| 5. 合入 | 见第 3 节 | 提出者批准，合入员决策 + 平台 git:auto-merge 执行 |

## 3. PR 合入责任

### 3.1 责任归属

| 角色 | 职责 |
|------|------|
| **提出者（仓库管理员）** | 合入的**最终批准者**，拥有合入权（缺席时见 4.6 替代裁决） |
| **合入员** | 合入的**决策者（专职，铁律 R21）**：汇总门禁结果、确认前置条件、冲突分级准入、判定放行（打 `status/merge-ready`）/阻断（打 `status/merge-blocked`）、合入后处理 |
| **平台 git:auto-merge** | 合入的**执行层**：`pull_request.mergeable` 事件下实际执行合入（squash + 删源分支），受 auto-merge-gate.sh 确定性门禁约束 |
| **路线图规划者** | 合入的**调度衔接者**：两圈收敛后唤醒合入员；不再亲自执行合入（铁律 R21） |
| **协作员·构建** | **构建门禁主审**：compile、产物一致性 |
| **协作员·测试** | **质量门禁主审**：lint、测试用例 |
| **协作员·审查** | **规范门禁主审 + 门禁复核**：命名/质量/越权审查，并对构建/测试门禁做四眼复核；冲突 C2 与合入员协作判定准入 |

### 3.1.1 分职门禁矩阵（谁主审 / 谁复核）

| 门禁项 | 主审 | 复核（四眼） | 通过标准 |
|--------|------|-------------|---------|
| 编译门禁 | 协作员·构建 | 协作员·审查 | exit 0 且 0 error，out/ 与 src/ 一致 |
| 质量门禁 | 协作员·测试 | 协作员·审查 | lint 0 error/warning，用例通过 |
| 规范门禁 | 协作员·审查 | 协作员·构建 | 命名项目规范分册全 [x] |
| 交叉审查收敛 | 协作员·审查 | 合入员 | 两圈无新增问题 |
| 合入总门禁 | **合入员** | 提出者（批准） | 3.2 五项全 [x] |

**四眼原则**：主审与复核必须**不同 NPC**；任何门禁主审与复核结论不一致 → 升级仲裁（第 4 章）。

### 3.2 合入前置条件（全部满足才可合入 · 打勾检查单）

```
☐ [ ] 两圈交叉审查收敛完毕，无新增问题 → 通过标准：评论含【最终结论】
☐ [ ] 无未决冲突 → 通过标准：所有上报均已答复（或按 4.6 缺席裁决已化解）
☐ [ ] 分职门禁矩阵全部 [x] → 通过标准：主审+复核结论一致且全绿
☐ [ ] 路线图状态 = 「待合入」→ 通过标准：状态字段已更新
☐ [ ] 提出者明确批准（或按 4.6 缺席规则）→ 通过标准：批准意见落于评论
```

**规则**：任一 `[ ]` 未打勾，合入员**不得**放行合入（R21）。

### 3.2.1 PR 状态标签流转（自动化状态机）

> 与分职门禁矩阵联动，全自动打标，无需人工干预：

| 阶段 | 触发 | 动作 |
|------|------|------|
| 门禁任一失败 | `pull_request` failStages | 打 `status/pending-fix`（待修改），移除 `status/merge-ready` |
| 合入员放行 | `pull_request` Stage 4 | 打 `status/merge-ready`（C0 全绿） |
| 合入员阻断 | `pull_request` Stage 4 / mergeable 复核 | 打 `status/merge-blocked`（C1-C3/否决） |
| 合入完成 | `pull_request.merged` | 打 `status/done`，移除 `pending-fix`/`merge-ready`/`merge-blocked` |

### 3.3 合入流程（打勾检查单 · 合入员决策 + 平台执行）

```
☐ [ ] ① 合入员汇总分职门禁矩阵结果 → 通过标准：矩阵五门禁全部 [x] 且复核一致
☐ [ ] ② 确认满足 3.2 → 通过标准：五项前置条件全部 [x]
☐ [ ] ③ 冲突准入（4.8）→ 通过标准：以 pr-gate 分级为输入，C2/C3 已按 4.8 处理
☐ [ ] ④ 提出者批准（或 4.6 缺席规则）→ 通过标准：批准意见落于评论
☐ [ ] ⑤ 判定放行 → 打 status/merge-ready 标签 → 通过标准：标签已打
☐ [ ] ⑥ 平台执行合入（pull_request.mergeable → auto-merge-gate → git:auto-merge；或合入员手动/CLI 执行）
        → 通过标准：PR 已合并
☐ [ ] ⑦ 合入后处理（pull_request.merged）：更新路线图为「已合入」+ 需求池「已实现」+ 文档巡检
        → 通过标准：状态与评论同步
```

> **双通道合入**：常规路径为 `pull_request.mergeable` 平台自动合入（C0 + 无否决标签）；
> 若 mergeable 事件未触发（如保护分支未配置 / 有 assignee 未通过），合入员可在 Stage 4 或
> `web_trigger` 中按上述检查单手动/CLI 执行合入（R21 仅合入员有权决策合入）。

## 4. 构建分歧处理

### 4.1 定义

构建分歧指在 **构建方案** 层面无法自行统一的争议，例如：tsconfig 配置变更、依赖版本取舍、模块/产物结构设计、是否引入构建工具等。区别于可定点化解的**代码缺陷**。

### 4.2 分级处理

| 级别 | 特征 | 处理方式 |
|------|------|---------|
| **L1 缺陷级** | 具体代码错误，可定点修复 | 交叉审查中直接定点化解，不升级 |
| **L2 方案级** | 影响构建方向 / 他人主责 / 无法局部化解 | 升级为冲突上报，停止改动等待提出者裁决 |

### 4.3 仲裁链（分歧无法内部统一时，逐级上移）

1. **约定**：是否已有明确规定 → 无条件遵守。
2. **主责领域**：争议落在谁的主责，谁有最终方案权；他者可提建议但不得覆盖。
3. **交叉审查共识**：若争议横跨主责（如构建方案影响测试），先在交叉审查中协商；能达成一致则按一致方案执行。
4. **提出者裁决**：仍无法一致 → 冲突上报，由提出者（仓库管理员）裁决，裁决为最终决定。
5. **提出者缺席**（超时未答复）→ 按 4.6 替代裁决机制处理，不无限等待。

**规则**：分歧未裁决前，涉及分歧的文件**冻结**（不得继续修改）；不冻结的文件可继续推进，保证不阻塞其它工作。

## 4.5 自动化审查（PR 自动触发 · 铁律 R11）

> 通过 `.cnb.yml` 的 `pull_request` 事件，PR 打开/更新时**自动**触发协作员·审查，无需人工 `@`。

### 4.5.1 触发时机

- PR 打开 / 推送新提交更新时自动触发（`pull_request` 事件）。
- 不依赖 `@` 提及；属于系统级自动检查（区别于 `pull_request.comment@npc` 的人工提及）。

### 4.5.2 审查范围（打勾检查单）

```
☐ [ ] 命名规范 → 通过标准：命名项目规范分册 1.2 全 [x]
☐ [ ] 门禁验证 → 通过标准：compile → lint → diff 全绿
☐ [ ] 改动质量 → 通过标准：无越权 / 无大重构 / 无硬编码 / 无缺 i18n
☐ [ ] 关联追溯 → 通过标准：PR 关联 意图 #ID / 需求 R#ID
☐ [ ] 输出审查结论 → 通过标准：【执行清单】回显 + 问题清单 + 修复建议
```

### 4.5.3 处理规则

1. **合规** → 输出【审查结论】无遗留，标注「通过」。
2. **可定点修复**（命名/小缺陷）→ 直接修复并说明。
3. **需人工**（方案级分歧/越权争议）→ 按第 4 章仲裁链处理，不擅自改。
4. **结论回写**：审查结论与修复记录写入 Issue/PR 评论 + 路线图。

## 4.6 管理员缺席时的替代裁决（防死锁 · 升级 + 超时自动裁决）

> 问题：冲突上报后管理员不在线，流程若无限等待则死锁。
> 方案：**风险分级 + 等待期 + 超时自动裁决**。管理员可随时回来推翻自动裁决（有损撤销须人工修正）。

### 4.6.1 缺席判定

```
☐ [ ] 冲突上报后等待期（默认 24h，可经约定讨论调整）→ 通过标准：评论含【上报时间】
☐ [ ] 等待期内提出者无答复 → 判定「管理员缺席」→ 通过标准：超时记录
☐ [ ] 缺席期间文件冻结 → 通过标准：涉及分歧文件未改动
```

### 4.6.2 风险分级自动裁决（管理员缺席时生效）

| 级别 | 特征 | 缺席时处理 |
|------|------|-----------|
| **L1 缺陷级** | 具体错误，可定点修复 | 按主责 + 交叉审查共识直接修复，不等待 |
| **L2 低风险方案** | 可回滚、不破坏主线、不涉及权限 | 默认按「最小风险路径」执行，评论记录【自动裁决】+ 理由，管理员可事后推翻 |
| **L2 高风险方案** | 破坏性变更 / 越权争议 / 合入决策 | **强制等待**管理员；不得自动裁决 |

### 4.6.3 自动裁决流程（打勾检查单）

```
☐ [ ] ① 确认缺席（超时未答复）→ 通过标准：等待期已过
☐ [ ] ② 风险分级 → 通过标准：L1 / L2低 / L2高 已判定
☐ [ ] ③ L2高 → 停止，标注「阻塞·等管理员」→ 通过标准：冻结持续
☐ [ ] ④ L1/L2低 → 执行自动裁决 → 通过标准：评论含【自动裁决】+ 理由 + 可回滚说明
☐ [ ] ⑤ 路线图标注「缺席裁决」→ 通过标准：状态 + 变更日志
☐ [ ] ⑥ 管理员回来可推翻 → 通过标准：推翻后人工修正 + 记录
```

### 4.6.4 越权红线

1. **L2 高风险绝不自动裁决**（合入、越权争议、破坏性变更）。
2. 自动裁决必须**可回滚**（有撤销路径才可执行）。
3. 自动裁决不改变主责归属，只做"风险最小化"的选择。
4. 每次自动裁决都须留痕（评论 + 变更日志），供管理员审计。

## 4.7 PR 门禁自动化系统（联动设计）

> 将 4.5 自动化审查与 3.1.1 分职门禁矩阵联动，形成**PR 门禁自动化闭环**。

### 4.7.1 触发与流转（事件驱动）

```
PR 打开/更新（pull_request 事件，无需 @）
  → $ 级统一前置门禁（pr-gate.sh）：幂等去重 → 冲突检测 → Diff 初筛 → 分级派单（防卡死）
  → 自动审查（4.5）：命名 → 门禁 → 质量 → 输出【审查结论】
  → 分职门禁矩阵（3.1.1）：构建主审/质量主审/规范主审 各自验证
  → 合入员汇总门禁矩阵（Stage 4）→ 全绿则打 status/merge-ready
  → 提出者批准（或 4.6 缺席裁决）→ pull_request.mergeable 事件 → auto-merge-gate.sh →
    合入员复核 → 平台 git:auto-merge 执行合入 → 合入员后处理 → 收官
```

> **防卡死机制（4.7.1 补）**：`pull_request` 事件会同时拉起构建/测试/审查/合入员 4 个 NPC，
> 若各自盲目并行、又互相等待对方结论，会形成死锁。故 `$` 级先执行 `.cnb/scripts/pr-gate.sh`
> 输出【门禁结论】（幂等去重 + 冲突分级 C0/C1/C2/C3 + Diff 初筛 + 分级派单），
> 各 NPC 读结论后按分级只让**本轮主导者**介入，避免重复拉起与互相等待。
> 幂等：同一 head commit 已审查（`status/gate-ok` 标签）则跳过，防级联无限触发。

### 4.7.2 自动化门禁检查单（PR 评论回显）

```
☐ [x] 自动审查已触发（pull_request 事件）
☐ [x] 编译门禁：主审构建 + 复核审查 → 通过
☐ [x] 质量门禁：主审测试 + 复核审查 → 通过
☐ [x] 规范门禁：主审审查 + 复核构建 → 通过
☐ [x] 交叉审查两圈收敛 → 通过
☐ [x] 合入总门禁：合入员汇总 → 通过（打 status/merge-ready）
☐ [ ] 提出者批准 / 缺席裁决 → 状态：<等待 / 已批准>
☐ [ ] 平台 git:auto-merge 执行合入（pull_request.mergeable，无 merge-blocked 否决）→ 通过
```

### 4.7.3 门禁失败处理

```
☐ [ ] 编译/质量/规范任一失败 → 定点修复后重跑门禁 → 通过标准：从失败点重置全链
☐ [ ] 主审与复核不一致 → 升级仲裁（4.3）→ 通过标准：不擅自定论
☐ [ ] 需要人工 → 标注「阻塞·需人工」→ 通过标准：评论 + 路线图状态同步
```

### 4.7.4 与自动化审查的关系

- **4.5 自动化审查** = 触发入口 + 首次扫描（发现即报）。
- **4.7 门禁自动化系统** = 完整闭环（审查 → 分职验证 → 汇总 → 批准/缺席 → 合入）。
- 两者共用打勾检查单与【执行清单】回显，数据写同一路线图。

### 4.7.5 自动门禁回写（PR 结果 → 路线图）

> 每个执行体的 `pull_request` 自动验证（构建门禁 / 质量门禁 / 规范门禁）结果须**自动回写路线图**，
> 供合入员合入总门禁汇总，且满足幂等（R16：路线图是唯一事实源）。

```
☐ [ ] 构建门禁通过 → 回写：路线图「构建门禁」= ✅ → 通过标准：版本号+1
☐ [ ] 质量门禁通过 → 回写：路线图「质量门禁」= ✅ → 通过标准：版本号+1
☐ [ ] 规范门禁通过 → 回写：路线图「规范门禁」= ✅ → 通过标准：版本号+1
☐ [ ] 任一失败 → 回写：标注 ✗ + 问题摘要 → 通过标准：待修复任务已建
☐ [ ] 三次回写全绿 → 路线图状态 = 「待合入」候选 → 通过标准：合入员可进入 3.3
```

**回写规则**：
1. 执行体完成 PR 自动验证后，按第 7 章硬约束更新路线图（占锁 → 版本+1 → 日志）。
2. 合入员汇总时读取路线图门禁回写区，与 PR 评论【构建/质量/规范结论】交叉核对。
3. 不一致 → 以实际门禁结果为准，修正路线图并记录。

### 4.7.6 全角色自动事件总览（代码事件驱动）

| 角色 | pull_request 自动入口 | pull_request.mergeable 自动合入 | web_trigger 调度入口 | 用途 |
|------|----------------------|-------------------------------|---------------------|------|
| 协作员·构建 | ✅ 构建门禁自动验证 | — | ✅ 确定性调度 | PR 触发构建检查；规划者调度构建任务 |
| 协作员·测试 | ✅ 质量门禁自动验证 | — | ✅ 确定性调度 | PR 触发质量检查；规划者调度测试任务 |
| 协作员·审查 | ✅ 规范门禁 + 四眼复核 | — | ✅ 确定性调度 | PR 自动审查；规划者调度审查任务 |
| 路线图规划者 | ✅ 规划/调度（建 PR 触发串联门禁） | — | ✅ 确定性调度 | 需求收集/调度/文档/巡视（合入移交合入员，R21） |
| 合入员 | ✅ 合入门禁（Stage 4 决策） | ✅ 自动合入复核 + merge-blocked 否决 | ✅ 确定性调度 | 合入决策/放行·阻断/合入后处理 |
| 平台 git:auto-merge | — | ✅ 执行合入（auto-merge-gate.sh 门禁后，allowAssigneeApprovedMerge） | — | 实际合入执行层 |
| `push` 事件防线 | — | — | — | 合入 main 后主分支构建验证（告警不阻断） |

**双通道完成**：任意 NPC 完成工作 → 推分支/建 PR（触发下游 pull_request）或 web_trigger
（确定性调度）→ 下游无需评论 @ 即可被触发（见索引三-1）。

## 4.8 合入冲突自动审查（冲突检测 → 自动唤醒 → 判定准入）

> **问题**：PR 合入时因目标分支与源分支改动重叠产生 **Git 合并冲突（merge conflict）**，
> 或冲突方改动**逻辑互斥**。此时不能盲目自动合并，须**自动唤醒自动化 NPC 审查后判定**：
> 改动是否合理达标、质量如何——**达标才可合入，否则禁止**。

### 4.8.1 冲突检测（触发时机）

```
☐ [ ] PR 合入前检测 Git 冲突 → 通过标准：git merge --no-commit 预演 / 平台合并检查报告
       （注：由 $ 级 pr-gate.sh 统一预演检测，输出冲突分级 C0/C1/C2/C3 供各 NPC 复用）
☐ [ ] 检测到冲突 → 进入 4.8.2 → 通过标准：冲突文件清单已列出
☐ [ ] 无冲突 → 走正常合入流程（3.3）→ 通过标准：不触发本节
```

### 4.8.2 冲突分级与自动唤醒

| 级别 | 特征 | 自动唤醒对象 | 处理 |
|------|------|-------------|------|
| **C1 可自动化解** | Git 三方合并可解 / 简单重复代码 | 冲突双方（构建/测试/审查，按主责映射） | 自动唤醒双方定点解决冲突，重跑门禁 |
| **C2 需审查判断** | 双方逻辑互斥 / 方案冲突 / 越权争议 | **协作员·审查**（主审）+ **合入员**（合入门禁） | 全面审查冲突改动，判定准入 |
| **C3 高危** | 数据迁移 / 破坏性变更 / 涉及核心逻辑 | **协作员·审查** + **官方 CodeBuddy 复核** + 提出者 | 强制人工复核，禁止自动合入 |

**自动唤醒方式（双通道）**：
1. `pull_request` 事件（冲突 PR 更新时自动触发，确定触发）。
2. `web_trigger`（规划者确定性调度审查执行体）。

### 4.8.3 冲突审查检查单（C2/C3 执行 · 打勾）

```
☐ [ ] ① 冲突点梳理 → 通过标准：列出 <冲突文件 + 双方改动 + 矛盾原因>
☐ [ ] ② 改动合理性 → 通过标准：改动与意图/需求一致，无越权（R2）
☐ [ ] ③ 质量门禁 → 通过标准：compile → lint → 测试 全绿
☐ [ ] ④ 冲突方案评估 → 通过标准：最小改动、不破坏他者主责逻辑
☐ [ ] ⑤ 关联追溯 → 通过标准：改动可追溯 意图 #ID / 需求 R#ID
☐ [ ] ⑥ 输出【冲突审查结论】→ 通过标准：【执行清单】[x]/[ ] 回显
```

### 4.8.4 判定门禁（达标才可合入 · 否则禁止）

```
判定 = ①②③④⑤ 全部通过 → 【准入：允许合入】→ 进入 3.3 正常合入
      = 任一项未通过     → 【禁止：合入阻塞】→ 标记「合入阻塞·需修复」
```

| 判定结果 | 动作 |
|---------|------|
| **准入（通过）** | 审查员输出【冲突审查结论：通过】→ 合入员按 3.3 决策放行（平台 git:auto-merge 执行） |
| **禁止（未通过）** | 输出【冲突审查结论：未通过】+ 问题清单 → 冲突方按清单定点修复 → 重跑门禁 → 重新审查 |
| **C3 高危** | 无论审查结论，强制等待提出者批准；未批准**禁止合入** |

### 4.8.5 禁止合入保护（硬约束）

```
☐ [ ] 冲突未解决 → 禁止合入 → 通过标准：合入门禁被阻断（状态「合入阻塞」）
☐ [ ] C2/C3 审查未通过 → 禁止合入 → 通过标准：不进入 3.3
☐ [ ] C3 无提出者批准 → 禁止合入 → 通过标准：PR 保持 open
☐ [ ] 结果回写路线图 → 通过标准：【冲突审查】状态 + 版本号+1
```

### 4.8.6 与既有机制的关系

- **2.5 冲突上报**：逻辑分歧（NPC 间方案矛盾）→ 走上报等待答复。
- **4.8 合入冲突**：Git/合入层面的冲突 → 自动唤醒审查判定准入。
- 两者互补：逻辑分歧未解决 → 升级为合入阻塞（4.8.5）；合入冲突审查中发现逻辑矛盾 → 回 2.5 上报。

## 7. 路线图更新机制（确保及时更新 · 硬约束）

**更新时机（强制性，任一发生即更新）：**

- 分工声明完成后 → 初始化本轮路线图条目
- 每个 NPC 每完成一步（构建 / 测试 / 审查）→ 更新对应进度
- 交叉审查每圈结束 → 记录审查对象、修复项
- 冲突上报 / 获得答复 → 更新状态（「冲突中·等待答复」→「已答复·按裁决执行」）
- 两圈收敛完成 → 更新为「待合入」
- 合入完成 → 更新为「已合入」并附最终结论

**硬约束（防"虚假及时"）：**

1. **版本控制**：每次更新版本号 +1，记录时间戳与操作者；冲突版本不得互相覆盖。
2. **更新锁（写锁）**：写前占锁（更新锁字段 = 自己的名字），写毕释放；锁超 15 分钟视为异常，他者可接管并记录。
3. **进度心跳**：领取任务的 NPC 每完成一步必须更新「最近心跳」；同一 NPC 连续 3 步未更新 → 判定卡阻，其余 NPC 按并行拓扑分册 10.7 介入。
4. **变更日志（追加式）**：每次更新追加一行（时间 / 版本 / 操作者 / 摘要），永不覆盖。
5. **双写校验**：路线图与 Issue 评论必须同步；不一致以 Issue 评论事实为准并修正路线图。
6. **不阻塞式更新**：每步完成即更新，不得攒到收尾一次性补写。
7. 路线图是下一轮意图的输入（NPC 开工前必须阅读）。

### 7.4 路线图分层结构

```
总体路线图（每轮意图一个）
├── 大点（路线图中要实现的大点，可多个）
│   ├── TODO 表（每个大点可拆出多个，每个 NPC 独占领取一个）
│   │   └── 任务（表内最小单元，带依赖关系）
└── 依赖拓扑（DAG）：跨表依赖 / 关键路径 / 并行支线
```

- **树的分叉**：大点 → 多个 TODO 表；TODO 表 → 多个任务。分叉处天然并行。
- **环的分叉**：依赖环（禁止）→ 冻结 + 上报；协作环（允许）＝流水线接力 + 两圈交叉审查。
- 每个 TODO 表由**一个 NPC 独占领取**，任务状态严格流转：`待领 → 进行中 → 完成·待交接 → 已交接`。

### 7.5 TODO 表格式

```
#### TODO 表 <表ID> · 领取者：<NPC>
| 任务 | 依赖 | 状态 | 负责 | 产物 |
|------|------|------|------|------|
| <任务ID> | <上游任务ID 或 -> | 待领/进行中/完成·待交接/已交接 | <NPC> | <可验证产物> |
```

领取即锁定：表内任务仅领取者可更新；他者只在交叉审查时读表并做定点补丁记录。
