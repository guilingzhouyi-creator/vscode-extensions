# NPC 约定索引（必读 · 铁律 · 文档指针地图）

> 本文档是 NPC 协作体系的**唯一入口**。它本身不展开细节，只提供：
> **引导式命令规范**（打勾/占位格式，全体系通用）+ **铁律**（不可违反）+ **文档指针地图**（按需加载的分册索引）+ **协作活性机制**（完成即唤醒·双通道 / 讨论修订）。
> 任何 NPC 开工前**必读本文档**；细节按需打开对应分册（见指针地图），无需一次通读全部。
>
> **触发机制要点（务必了解）**：
> 1. **角色名精确匹配（防事件跳过）**：CNB 要求 @ 提及的角色名与 `.cnb/settings.yml` 的
>    `npc.roles[].name` **完全一致**，且**不带 `@` 前缀、不带括号**。错误格式 `@cnb/<仓库>(角色名)`
>    会导致角色名不匹配 → **事件被跳过**、走系统默认行为。正确格式：`@协作员·构建` / `@路线图规划者`。
>    本仓库精确角色名：`协作员·构建` / `协作员·测试` / `协作员·审查` / `路线图规划者` / `合入员`。
> 2. `issue.comment@npc` 触发者被文档定义为"当前操作者"；**NPC 自己评论中的 `@` 无法触发其他 NPC**
>    （平台机制，实际运行已验证）。因此本体系唤醒采用**确定性通道**（见三-1，2026-08-21 已修复配置）：
>    - ① 代码事件驱动（建分支/PR → `$ pull_request` 系统事件自动串联三执行体门禁 + 合入员合入门禁）为主；
>    - ② `api_trigger_npc`（CNB CLI `cnb build start-build`）精确调度单个 NPC；
>    - ③ `web_trigger`（页面/API）手动调度；评论 `@` 仅作通知留痕。详见三-1。

## 〇、引导式命令规范（全体系通用 · 打勾占位）

> **为什么**：NPC 对"散文式约束"解析弱、易遗漏。本体系所有流程一律采用**引导式命令**——
> 用 `[ ]` 打勾、`<占位符>` 填空、`→ 通过标准` 判定，把"约束"变成"可勾选、可验证、可追溯"的命令。
> **执行时**：先逐项打勾确认，再进入下一步；未通过标准不得继续。

### 0.1 三种命令标记（所有分册统一使用）

| 标记 | 含义 | 用法示例 |
|------|------|---------|
| `[ ]` / `[x]` | 检查项：未完成 / 已完成 | `[x] 读取铁律与路线图` |
| `<...>` | 占位符：必须填写，不得省略 | `【领取】<表ID> + <领域> + <计划用时>` |
| `→ 通过标准` | 判定线：满足才算完成该项 | `→ 通过标准：exit 0 且 0 error` |

### 0.2 打勾检查单（Checklist）标准格式

```
☐ [ ] 步骤 1：<动作> → 通过标准：<可验证结果>
☐ [ ] 步骤 2：<动作> → 通过标准：<可验证结果>
☐ [x] 步骤 3：<动作> → 通过标准：<可验证结果>（示例：已完成）
```

- 每步**必须**写通过标准（命令式而非描述式）。
- 全部 `[x]` 才算完成；存在 `[ ]` 时**不得**宣称完成。

### 0.3 占位命令（Form Command）标准格式

```
【命令名】<必填参数1> + <必填参数2> + <可选参数?选填>
```

- 占位符内**必须填入实际值**，不得回显 `<...>` 本身。
- 缺失参数＝命令无效，需补全后才能生效。

### 0.4 输出命令（强制回显格式）

每条命令执行后，评论须**逐项回显**完成状态，例如：

```
【执行清单】
☐ [x] 读取铁律与路线图
☐ [x] npm install（exit 0）
☐ [ ] npm run compile → 失败，已报告原因
```

- 回显即证据：提出者 / 同侪据此判断是否真实完成。
- **未回显视为未执行**；同侪可要求补正（完成即唤醒协议）。

### 0.5 判定原则

1. **无标准不执行**：任何步骤缺"通过标准"时，先补齐标准再执行。
2. **失败即停**：某步未过标准，停止并上报，不得跳到下一步。
3. **打勾≠敷衍**：打勾必须与真实输出一致；发现虚假打勾视为违规。

## 一、铁律（不可违反 · 无需讨论）

以下规则是协作体系的底线，**任何情况下不得违背**；违反即视为越权，可被任何同侪上报：

| # | 铁律 | 依据 |
|---|------|------|
| R1 | 三职能于一身：构建 / 测试 / 审查每个 NPC 都具备；主责仅决定切入点 | 角色分册 |
| R2 | 不越权：不替代他者主责整体实现；不重写他者已通过实现；不做非必要大规模重构 | 角色分册 |
| R3 | 冲突未获提出者答复前，不得强行推进或覆盖他者改动 | 协作分册 |
| R4 | 门禁顺序不可调换：`npm install → compile → lint → diff`；失败从头重跑 | 治理分册 |
| R5 | 依赖环（A→B→A）禁止：发现即冻结 + 上报 | 拓扑分册 |
| R6 | 规划者不写实现代码；合入必须满足全部前置条件且经提出者批准（合入决策归合入员，见 R21） | 规划分册 |
| R7 | 路线图 / 需求池更新受硬约束（版本号 / 更新锁 / 心跳 / 变更日志） | 治理分册 |
| R8 | 协作约定与配置文件仅管理员可改；NPC 只能提修订建议 | 本索引 · 三-3 |
| R9 | 命名与项目规范强制：NPC/文档/代码/提交/评论命名遵循命名项目规范分册 | 命名项目规范分册 |
| R10 | 输出必须【执行清单】回显，未过标准即停；禁止虚假打勾 | 本索引 · 〇 |
| R11 | 自动化审查：PR 自动触发审查（pull_request 事件），不依赖人工 @ | 治理分册 · 自动化审查 |
| R12 | 合入门禁分职 + 四眼复核：编译/质量/规范门禁主审与复核必须不同 NPC；全绿才可合入 | 治理分册 · 分职门禁矩阵 |

| R15 | 回滚协议：错误改动用 git revert 定点回滚并重跑门禁；高风险回滚需表决/批准 | 容错兜底分册 · 回滚协议 |
| R16 | 幂等保护：路线图是唯一事实源，重复触发先查重，已完成不重做 | 容错兜底分册 · 幂等保护 |
| R17 | 超时兜底：各环节超时按升级链（执行体→审查→规划→管理员）逐级上移，不无限等待 | 容错兜底分册 · 超时兜底 |
| R18 | 合入冲突准入：Git 冲突/逻辑互斥 → 自动唤醒审查（C1-C3 分级）→ 达标才可合入，不达标禁止；C3 高危强制等提出者 | 治理分册 · 合入冲突自动审查 |

## 三、协作活性机制（引导而非写死）

约定不是"写死的配置"，而是**引导**。两套机制保证约定随实践进化、且流程不因死规则而僵化：

### 1. 完成即唤醒（接力协议 · 双通道）

**原则：任务完成后，执行者不"躺平等待"，而是主动唤醒流程中的下一个平权 NPC；规划者作为调度者，在任何需要时也有权唤醒执行体。唤醒是双向的。**

> **触发机制审查（重要 · 已验证）**：CNB 文档确认 `issue.comment@npc` 的"触发者为当前操作者"。
> **实际运行已验证：NPC 自己写的评论 `@` 无法触发其他 NPC**（规划者在问题区评论 @ 执行体，
> 对方无响应——事件被跳过）。因此唤醒**必须**用确定性通道，评论 `@` 仅作通知留痕。

> **配置修复（2026-08-21）**：`pull_request` / `pull_request.merged` / `api_trigger_npc` /
> `web_trigger` 等**确定性通道事件**已统一挂载到 `.cnb.yml` 的 `$` 下（兜底全分支）。
> ⚠️ 此前 `pull_request` / `web_trigger` 误挂在 NPC 角色名顶层 key 下（角色名只匹配 NPC 事件），
> 导致 PR 从未触发构建。现修正后：**建 PR 即自动串联「构建→测试→审查→合入」四段门禁**，
> 规划者无需再单独触发执行体。

**A. 主通道：代码事件驱动（确定触发 ✅ · 已修复）**

| 场景 | 完成者动作（推分支/建 PR） | 触发事件 | 下游 |
|------|--------------------------|---------|------|
| 级联启动 | 建分支 `feat/<意图>-<领域>` + 创建 PR | `pull_request`（PR 打开/更新自动触发） | 流水线内依次执行：构建门禁→质量门禁→审查门禁→合入门禁 |
| 构建门禁 | 三执行体按序（构建→测试→审查）在同一 PR 流水线中执行 | `pull_request` | 各自输出【结论】到 PR 评论 |
| 合入门禁 | 三执行体门禁完成后，合入员在同流水线收尾 | `pull_request` | 合入员汇总门禁矩阵、判定放行/阻断（打 merge-ready / merge-blocked） |
| 自动合入 | PR 满足 mergeable（无冲突+评审通过+保护分支） | `pull_request.mergeable` | auto-merge-gate.sh → 合入员复核 → 平台 git:auto-merge 执行合入 |
| PR 合入后 | 合入成功后自动触发 | `pull_request.merged` | 合入员做合入后处理（文档巡检/需求池更新/清标签） |

**B. 调度通道：CNB CLI / api_trigger / web_trigger（确定触发 ✅）**

- **CNB CLI + api_trigger_npc**（默认镜像已装 `@cnbcool/cnb-cli`）：规划者流水线内执行
  `cnb build start-build --repo <仓库> --branch <分支> --env role=协作员·构建 --env userPrompt="..."`
  可**精确触发单个 NPC**（通过 `env.role` 选择）；CNB_TOKEN 自动注入。
- **web_trigger**：页面按钮手动触发（传 userPrompt 交办）。
- 规划者唤醒执行体优先用此通道（见规划调度分册 5/5.1）。

**C. 辅助通道：评论 `@`（仅通知留痕 ⚠️）**

评论 `@` 用于**通知与留痕**（告知同侪/规划者已交接、需关注），**不作为触发手段**。

| 场景 | 完成者动作 |
|------|-----------|
| 交叉审查（2.3） | 完成自己的交叉审查后，评论 `@` 下一个应审查者并推送进展（配合 PR 事件） |
| 两圈收敛完成 | 唤醒「合入员」声明「两圈收敛完成，待合入」（确定性通道：PR/web_trigger 触发 role=合入员） |
| 卡阻 | 停滞者 `@` 同侪声明原因或让出表（见并行拓扑分册 10.7） |

**D. 调度通道：规划者 → 执行体（api_trigger / web_trigger）**

| 场景 | 规划者动作 | 确定性 |
|------|-----------|--------|
| 级联启动 | 需求达阈值 → 建分支/PR 触发 `$ pull_request` 串联门禁，或用 `cnb build start-build` 触发 `api_trigger_npc` | ✅ 确定 |
| 追加 / 变更需求 | 更新路线图 + 建分支/PR 或 CLI 触发 | ✅ 确定 |
| 重排优先级 | 更新路线图 + CLI 触发 `api_trigger_npc` | ✅ 确定 |
| 验证 / 修复请求 | 通过 CLI 触发 `api_trigger_npc`（指定 role）定点修复 | ✅ 确定 |
| 启动下一批 | CLI / 建 PR 触发下一批 | ✅ 确定 |
| 文档巡检发现遗留 | 评论 @ 提醒补正（辅助） | ⚠️ |

**唤醒格式**：`【唤醒】@<NPC>：<交接物/结论> + <请你执行的部分>`。
**双通道原则**：
1. **事件优先**：能通过代码事件（push/PR）触发的，必须用事件驱动（确定、可追溯）。
2. **评论 @ 为辅助**：评论 @ 负责通知留痕，不单独作为触发依赖。
3. **CLI/web_trigger 兜底**：规划者调度执行体时优先用 `cnb build start-build` 触发 `api_trigger_npc` 精确指定角色。
4. **未主动唤醒**＝违反活性机制，可被同侪提醒或按心跳判定卡阻。

### 2. 讨论修订（活文档机制）

**原则：约定是可讨论、可演化的"活文档"，而非冻结的规范；但修订必须受控。**

| 修订对象 | 谁能发起 | 谁能定稿 |
|---------|---------|---------|
| 铁律（本索引第一节） | 任何 NPC 提修订建议 | 仅提出者（管理员） |
| 分册细则（流程/并行/规划等） | 任何 NPC 在 Issue 发起【约定讨论】 | 平权表决多数通过（1:1 平票 → 提交管理员） |
| 参数（阈值 / 轮次 / 容量等） | 任何 NPC 提议 + 理由 | 平权表决多数通过 |
| 路线图 / 需求池内容 | 按 DRI（见门禁治理分册） | DRI |

**讨论流程**：
```
1. 发起：任一 NPC 在 Issue 评论发【约定讨论】<主题>：现状 + 问题 + 建议修改
2. 讨论：其余 NPC 发表意见（每人至多一条主张），提出者可选参与
3. 表决：涉及分册细则/参数 → 平权表决（多数通过，平票交管理员）
4. 落盘：通过后由 DRI 更新分册，递增版本号，变更日志留痕
5. 生效：落盘即生效；未通过则维持现状（先遵守，再讨论）
```

**引导原则**：遇到约定未覆盖的情况，NPC 优先按铁律与精神行事，同时在评论中发起【约定讨论】补齐约定——**先按引导执行，再把经验固化为约定**。

### 3. 修订权限总纲

- 本索引（铁律）与 `.cnb.yml` / `.cnb/settings.yml`：**仅管理员**可直接修改；NPC 提建议。
- 各分册：经讨论表决后，由对应 DRI 修改（DRI 见门禁治理分册 7.1）。
- 路线图 / 需求池：按 DRI 责任制，执行中实时更新（硬约束见治理分册 7.3）。
