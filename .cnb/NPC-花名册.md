# NPC 花名册（单一权威身份登记表）

> 本文件是仓库全部 NPC 的**唯一权威身份登记**，防止"互不知情"：
> 任何 NPC 开工前必读，明确"有谁、怎么叫、怎么找、谁干什么、谁管什么文档"。
> 配套：`.cnb/NPC-约定索引.md`（铁律+指针地图）、`.cnb/NPC-路线图.md`（执行状态）。
> **角色名必须精确匹配 `.cnb/settings.yml` 的 `npc.roles[].name`，否则事件跳过（见索引触发要点）。**
> **读取范围**：必读区 §1 总表 + §2 唤醒通道；选读区 §3 协作关系图 / §4 DRI / §5 常读文档（需要时）。禁止通读全文。

## 2. 唤醒通道（怎么找对方 · 确定性通道优先）

> **2026-08-21 配置修复**：`pull_request` / `pull_request.merged` / `api_trigger_npc` /
> `web_trigger` 已统一挂载到 `.cnb.yml` 的 `$` 下（兜底全分支）。角色名顶层 key 只匹配 NPC 事件。
> **建 PR 即自动串联「构建→测试→审查→合入」四段门禁**；`cnb build start-build` 触发 `api_trigger_npc`
> 可精确调度单个 NPC。

| NPC | `$ pull_request` 自动门禁 | `pull_request.mergeable` 自动合入 | `api_trigger_npc` CLI 精确调度 | `web_trigger` 页面手动 | `@` 提及（辅助） |
|-----|--------------------------|--------------------------------|-------------------------------|----------------------|------------------|
| 协作员·构建 | ✅ 构建门禁（自动，无需 @） | — | ✅ 指定 role=协作员·构建 | ✅ | `@协作员·构建` |
| 协作员·测试 | ✅ 质量门禁（自动，无需 @） | — | ✅ 指定 role=协作员·测试 | ✅ | `@协作员·测试` |
| 协作员·审查 | ✅ 审查门禁（自动，无需 @） | — | ✅ 指定 role=协作员·审查 | ✅ | `@协作员·审查` |
| 路线图规划者 | ✅ 规划/调度（建 PR 触发串联门禁） | — | ✅ 指定 role=路线图规划者 | ✅ | `@路线图规划者` |
| 合入员 | ✅ 合入门禁（Stage 4 决策） | ✅ 自动合入复核（Stage 1）| ✅ 指定 role=合入员 | ✅ | `@合入员` |
| （平台执行层） | — | ✅ `auto-merge-gate.sh` + `git:auto-merge` 执行合入 | — | — | — |

**触发格式铁律**：`@` 后必须用**精确角色名**（如上表第一列），勿用 `@cnb/<仓库>(角色名)` 括号格式（会跳过事件）。
**唤醒铁律（已验证）**：NPC 之间**不可用评论 @ 触发**（触发者为操作者）；唤醒必须用
代码事件（推分支/建 PR）/ CNB CLI（`cnb build start-build --env role=...`）/ web_trigger 任一确定性通道，
评论 @ 仅作通知留痕。

## 3. 协作关系图（谁审查谁 / 谁唤醒谁）

```
                ┌─────────────┐
                │ 仓库管理员    │  (下发意图/最终批准合入/裁决)
                └──────┬──────┘
                       │ @提及 / web_trigger
                 ┌─────▼─────┐
                 │ 路线图规划者 │  (需求收集/统计/规划/调度/文档DRI/巡视)
                 └─────┬─────┘
              web_trigger / 代码事件 │ 级联启动
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
  ┌─────────┐    ┌─────────┐    ┌─────────┐
  │协作员·构建│    │协作员·测试│    │协作员·审查│  (收尾把关)
  └────┬────┘    └────┬────┘    └────┬────┘
       └──交叉审查──▶测试│◀──交叉审查──┘
              构建──交叉审查──▶审查│◀──审查两者
                        │ 两圈收敛「待合入」
                        ▼
                ┌─────────────┐
                │    合入员     │  (合入门禁汇总/冲突准入/放行·阻断/合入后处理)
                └──────┬──────┘
                       │ 决策：status/merge-ready / merge-blocked
                       ▼
          ┌──────────────────────┐
          │ 平台 git:auto-merge   │  (pull_request.mergeable 事件执行实际合入)
          └──────────────────────┘
```

**交叉审查顺序（按序不得跳序）**：
```
协作员·构建 → 审查 协作员·测试 的改动
协作员·测试 → 审查 协作员·构建 的改动
协作员·审查 → 审查 协作员·构建 + 协作员·测试（收尾）
```

**唤醒接力**：任务完成后，通过代码事件（推分支/建 PR → pull_request）或 web_trigger 唤醒下一个 NPC（双通道，见索引三-1）；评论 @ 仅辅助通知。

## 6. 维护规则

1. **变更通知**：新增/改名/改职责 NPC → 管理员更新花名册 + settings.yml，并告知全体。
2. **一致性校验**：花名册角色名必须与 settings.yml 一致；发现不一致 → 以 settings.yml 为准并修正花名册。
3. **DRI**：花名册由路线图规划者维护（保持最新），管理员有权修订。
4. **与索引关系**：花名册是"身份登记"（谁），索引是"行为规范"（怎么干）——两者互补，不重复。
