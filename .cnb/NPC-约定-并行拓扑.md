## 1. 分工机制（接受到管理员意图后）

### 1.1 意图解析

先识别意图所属类型，再映射主责：

| 意图类型（示例） | 主责 NPC |
|-----------------|---------|
| 构建类：编译 / 打包 / 产物 / 构建配置 / 依赖 | 协作员·构建 |
| 测试类：补测试 / 跑 Lint / 质量校验 / 缺陷修复 | 协作员·测试 |
| 审查类：全面审查 / 冲突排查 / 收尾把关 / 合入前验证 | 协作员·审查 |
| 综合类：新功能 / 重构 / 跨层改动 | 全部按主责切入 |

### 1.2 分工规则

1. **提及即上岗**：被 `@` 提及的 NPC 必须承接其主责领域对应的部分。
2. **单兵全职能**：若意图只提及一个 NPC，该 NPC 以三职能全权执行（构建 → 测试 → 审查自查）。
3. **多者分工**：若意图提及多个 NPC，各以主责切入；主责不重叠，杜绝重复劳动。
4. **分工声明**：每个 NPC 开工前，在 Issue 评论声明【承接领域 + 计划产出】，避免重复或遗漏。
5. **未提及不越主责**：未提及的 NPC 不主动承接整体任务，仅在交叉审查阶段参与。

### 1.3 进度同步

- 每个 NPC 每完成一步，即按门禁治理分册第 7 章更新路线图（含各自主责领域的进度）。
- 综合类意图下，三个 NPC 并行推进，互不阻塞；交叉审查统一在收尾阶段按序进行。

## 2. 大意图与连续构建的平权并行协作

> 适用场景：意图**很大、涉及多方面、具有连续构建性**（模块 A 的产物是模块 B 的输入）。

### 2.1 任务分解（WBS，先分解后执行）

1. 三个 NPC 共同将大意图拆解为**最小可独立完成的任务单元**，每单元必须：
   - 单一职责（属于一个领域：构建 / 测试 / 审查）
   - 依赖清晰（标注上游单元；无依赖则进入共享池）
   - 产物明确（交付物可被下游消费 / 可单点验证）
   - 体积可控（可在一轮门禁内完成）
2. 分解结果写入路线图任务矩阵（2.8），并 @ 全体确认；任一 NPC 可提出调整，共识通过即生效。
3. 分解共识达成前，不领取任务。

### 2.2 依赖图与关键路径

- 依据单元依赖关系建立**依赖图**，识别：
  - **连续构建链**（必须按序的串行链）：如 `基线构建 → 模块A → 依赖A的模块B → 全量产物`
  - **可并行支线**（互不依赖的单元）：可同时分给三个 NPC
- **关键路径原则**：连续构建链决定最短总工期；支线任务全部并行消化，不占用关键路径时间。

### 2.3 任务领取（平权分配 · 占位命令）

**领取命令（必须完整填空，缺失参数无效）：**

```
【领取】<单元ID> + <领域:构建/测试/审查> + <计划用时> + <依赖就绪确认:是/否>
```

**领取规则（打勾检查单）：**

```
☐ [ ] 依赖已就绪（或无依赖）→ 通过标准：上游状态 = 已交接 / 无依赖
☐ [ ] 未超在途上限 → 通过标准：单 NPC 在途任务 ≤ 2
☐ [ ] 不越主责 → 通过标准：未领取他者主责整体实现
☐ [ ] 写入任务矩阵「负责」列 → 通过标准：矩阵含 <单元ID>→<NPC>
```

**争抢裁决（平权）**：两 NPC 同时声明同一单元 → 主责匹配者优先；都匹配/都不匹配 → 先声明者得；仍存疑 → 协作员·审查协调（只按 2.6 表决）。

### 2.4 连续构建的流水线接力（异步构建 · 完成即唤醒 · 占位命令）

**交接命令（上游完成时发布）：**

```
【交接】<单元ID> + <产物路径> + <接口契约> + 【唤醒】@<下游>：<请你执行的部分>
```

**交接验收检查单（下游收到时执行）：**

```
☐ [ ] 收到交接物（产物 + 契约）→ 通过标准：产物存在、契约可读
☐ [ ] 先定契约后实现 → 通过标准：接口（类型/路径/约定）已对齐
☐ [ ] 跑最小门禁（npm run compile）→ 通过标准：exit 0
☐ [ ] 通过 → 继续开工；失败 → 反馈上游定点修复 → 通过标准：上游修复后重新交接
```

**要点**：下游拿到交接物即可开工，无需等待整条链完成；由此"串行大链"变"流水线"，三 NPC 插空并行。

### 2.5 同步点（只在必需处汇合）

| 同步点 | 时机 | 动作 |
|--------|------|------|
| **A. 分解共识** | 任务分解完成时 | 全体确认任务矩阵，之后才允许领取 |
| **B. 交叉审查** | 领取的单元全部完成、交接物就绪时 | 进入两圈交叉审查 |
| **C. 合入前** | 两圈收敛完成后 | 执行合入（门禁治理分册第 3 节） |

同步点等待机制：先到者把结果写入任务矩阵并标注「就绪」，最后一个到齐者触发下一阶段（不设领导，由事件顺序自然触发）；也可由完成者主动 `@` 唤醒下一位（完成即唤醒）。

### 2.6 平权决策（无领导表决）

1. 涉及任务分配、分解调整、顺序争执等**程序性**问题：每 NPC 一票，**多数通过**。
2. 平票（1:1:0）→ 按优先级：约定铁律 > 主责领域归属 > 上报提出者裁决。
3. 涉及**方案性**分歧 → 仍按门禁治理分册第 4 章分级处理，不因并行而跳过仲裁。
4. 任何 NPC 不得以"效率"为由独断；平权是底线。

### 2.7 负载均衡与空闲认领

1. 空闲 NPC 主动扫描任务矩阵，认领「无主且依赖就绪」的单元（Pull 而非 Push）。
2. 若某 NPC 卡在关键路径，其余 NPC 按 2.4 接力配合，不抢其主责。
3. 连续构建链任一环停滞 → 由停滞者上报原因；其他人继续消化支线，不停摆。
4. 全部支线消化完、关键路径完成 → 进入同步点 B。

### 2.8 任务矩阵（写入路线图）

```
任务矩阵（意图 <ID>）：
| 单元 | 领域 | 依赖 | 状态 | 负责 | 产物 |
|------|------|------|------|------|------|
| T1   | 构建 | -    | 完成 | 构建 | 基线可编译 |
| T2   | 测试 | T1   | 进行中 | 测试 | 单测+lint |
| T3   | 审查 | T2   | 待领 | -    | diff 审查 |
连续构建链：T1 → T2 → T3（流水线接力）
同步点：A(分解共识) / B(交叉审查) / C(合入)
```

**状态取值**：待领 / 进行中 / 完成·待交接 / 已交接 / 卡阻·已上报

## 3. 分层任务拓扑（路线图 → 大点 → TODO 表 → 任务）

### 3.1 四层结构定义

| 层 | 定义 | 数量关系 | 谁维护 |
|----|------|---------|--------|
| **L1 总体路线图** | 每轮意图一个，顶层状态与依赖拓扑 | 1 : N 大点 | 全员（硬约束） |
| **L2 大点** | 路线图中要实现的大点（里程碑式可交付块） | 1 : N TODO 表 | 全员 |
| **L3 TODO 表** | 每个大点拆出的多个表，**每个 NPC 独占领取一个** | 1 : N 任务 | 领取者独有 |
| **L4 任务** | 表内最小单元，带依赖关系（同一表或跨表） | 依赖成 DAG | 领取者 |

### 3.2 分解规则（自上而下，逐层共识）

1. **L1→L2**：三个 NPC 共同把意图拆成大点；大点须：可独立验收、依赖清晰、体积可控。
2. **L2→L3**：每个大点拆成多个 TODO 表（按领域与依赖拆分）；**一个大点必然产生 ≥2 个 TODO 表**才构成分叉并行；单表不可过大。
3. **L3→L4**：领取者在自己表内拆任务，任务粒度以"可单步完成并验证"为准。
4. 每层分解结果写入路线图；同步点 A 在 L2 完成时触发，L3 领取在 L2 共识后并行进行。

### 3.3 树状分叉（并行源）

- **L2 分叉**：多个大点互不依赖 → 可分派不同 NPC，跨大点并行。
- **L3 分叉**：大点内多个 TODO 表 → 由三个 NPC 各领一个，表间并行。
- **L4 分叉**：表内无依赖任务 → 领取者按主责顺序消化。
- 分叉原则：**凡无依赖即可并行**；并行度上限 = 3（三 NPC），同一 NPC 在途 TODO 表 ≤ 2。

### 3.4 依赖拓扑（DAG · 顺序 + 异步并行）

- 任务依赖关系构成**有向无环图（DAG）**：关键路径（串行链）+ 并行支线 + 跨表依赖。
- **跨表依赖**：任务可依赖他者 TODO 表中的任务（如构建表 T1-B3 依赖测试表 T1-T1），据此形成流水线接力。
- **DAG 声明**：每轮意图在路线图顶部声明「依赖拓扑」，含跨表依赖、关键路径、并行支线三项。

### 3.5 环的分叉（依赖环 vs 协作环）

| 环类型 | 定义 | 处理 |
|--------|------|------|
| **依赖环（禁止）** | 任务依赖成环：A→B→A，DAG 失效（铁律 R5） | 发现者立即**冻结**相关任务 + 冲突上报；由提出者裁决打断环 |
| **协作环（允许）** | 流水线接力环（构建→测试→审查→合入）与两圈交叉审查 | 正常协作循环 |

**依赖环检测**：任一 NPC 在领取/更新任务时发现「自己的任务依赖链上出现自己」或「跨表依赖互相引用成环」→ 即判定依赖环，冻结 + 上报，不得自行改依赖破环（改拓扑属方案级分歧）。

### 3.6 TODO 表领取与独占

1. **领取即锁定**：NPC 声明【领取 TODO 表 <表ID>】后，该表独属于该 NPC（写权限独占）。
2. 领取约束：优先主责领域；单 NPC 在途 TODO 表 ≤ 2；未完成当前表前不得领同大点的第二个表。
3. 表内任务状态严格流转：`待领 → 进行中 → 完成·待交接 → 已交接`；不可跳变；异常 → `卡阻·已上报`。
4. 他者只读该表；交叉审查时的定点修复须在变更日志记录「代修」并通知表主确认。

### 3.7 进度心跳与卡阻介入

1. 每个领取 TODO 表的 NPC 每完成一步更新「最近心跳」。
2. **连续 3 步未更新心跳** → 判定卡阻：其余 NPC 在路线图标注「卡阻·已上报」，上报停滞者；停滞者须在 1 次心跳内说明原因或让出该表。
3. **让表机制（平权）**：停滞者让出 TODO 表 → 其余 NPC 按主责匹配 + 先声明先得接表，接表者重跑未完成任务的最小门禁。
4. 关键路径上无 NPC 卡阻时，支线表可继续并行，不停摆。

### 3.8 回并与收官

1. TODO 表内任务全部「已交接」→ 表标记「完成·待回并」。
2. 大点聚齐全部子表「完成」→ 大点标记「完成」，触发该大点交叉审查。
3. 全部大点完成 + 两圈收敛 → 进入同步点 C（合入）。
4. 合入后路线图标记「已合入」，变更日志收官。

## 4. 异步平权协作规范化（总则 · 打勾检查单）

> 本仓库采用**异步 + 平权**协作模型：无领导、无独裁，事件驱动 + 占位命令。规范如下。

### 4.1 异步协作规范

```
☐ [ ] 无依赖即并行 → 通过标准：不等待无关任务
☐ [ ] 有依赖即接力 → 通过标准：上游交接后下游立即开工
☐ [ ] 完成即唤醒 → 通过标准：【唤醒】@<下一个 NPC>
☐ [ ] 空闲即认领 → 通过标准：扫描任务池 Pull 无主且依赖就绪的单元
☐ [ ] 不停摆 → 通过标准：关键路径停滞时，其他人继续消化支线
☐ [ ] 心跳驱动 → 通过标准：每步完成更新「最近心跳」
```

### 4.2 平权决策规范

```
☐ [ ] 程序性问题 → 平权表决多数通过 → 通过标准：2/3 多数
☐ [ ] 平票(1:1) → 按 铁律 > 主责归属 > 上报提出者 → 通过标准：优先级链
☐ [ ] 方案性分歧 → 走门禁治理分册仲裁链 → 通过标准：不因并行跳过仲裁
☐ [ ] 禁止独断 → 通过标准：无 NPC 以"效率"为由单方决定
```

### 4.3 并发安全规范（防冲突）

```
☐ [ ] 独占写 → 通过标准：TODO 表仅领取者可写
☐ [ ] 更新锁 → 通过标准：路线图写前占锁、写毕释放
☐ [ ] 版本号 → 通过标准：每次更新 +1，冲突版本不覆盖
☐ [ ] 定点修复 → 通过标准：代修记录 + 通知表主
☐ [ ] 依赖环检测 → 通过标准：发现即冻结 + 上报（R5）
```

### 4.4 异步协作状态机（统一流转）

```
待领 → 进行中 → 完成·待交接 → 已交接 → （回并）→ 待合入 → 已合入
                ↘ 卡阻·已上报 → 让表/接表 → 重新进行中
```

- 状态跳变**必须经由对应命令**（领取/交接/唤醒/上报），不可直接改写。
- 状态与路线图、Issue 评论三处一致（双写校验）。
